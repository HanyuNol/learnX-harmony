# ADR-0009：登录收尾以"漫游票据"建会话为主，重新登录降为兜底

## 状态

已接受（2026-09-27 用户确认；ADR-0008 中"建会话方式"的措辞已由本决策取代）

## 背景

ADR-0008 决定登录由 WebView 主导，并规定认证完成后**停止页面导航、取用抓到的表单数据**
来建立会话（`LearnClient.loginWithFormData` 最初就按"原样重放页面那份 SM2 密文"实现）。

真实账号（已启用多因子认证）实测推翻了这条路径：

1. **原样重放行不通**：`i_pass` 是页面用**它那一次会话**的 SM2 公钥加密的，密文与会话绑定；
   我们的重放请求拿不到漫游工单，服务端返回的响应既无工单也不含「二次认证」字样，
   于是被归成"学号或密码错误"——把会话问题误报成了密码问题。
2. **改成"带设备信任标识重新登录"后依然走不通**：该路径要求服务端把本机认成
   **已登记的信任浏览器**；而校方页面会判定"浏览器处于隐私或匿名模式"并给出警告，
   用户每次登录都被要求输入验证码。对开启多因子认证的账号，任何"重新认证"都会被再要一次
   验证码——纯 API 重放在原理上不可依赖。
3. **可行的那条路一直就在手边**：认证完成后页面会导航到
   `…/f/j_spring_security_thauth_roaming_entry?ticket=<票据>`；我们在 `onLoadIntercept`
   取消这次导航时，**票据就在那个 URL 里**（实测 ticket 长度 36）。

## 决策

**登录收尾以"漫游票据"为首选路径**：

1. `onLoadIntercept` 命中漫游地址时，除取消导航外**同时记下该 URL**；
2. 首选：`LearnClient.loginWithRoamUrl` 用这个 URL 直接发起漫游 → 取首页 CSRF。
   **刻意不清 Cookie**——浏览器自己发这一步时也带着会话，保持上下文一致；
3. 兜底：没截到票据、或票据漫游失败时，才回退到"带页面生成的设备信任标识重新登录"
   （从表单体取 `fingerPrint` / `fingerGenPrint` / `fingerGenPrint3`）；
4. 两条路径都记日志标明走了哪条（`建会话方式=漫游票据|重新登录`）。

ADR-0008 的其余决策**不变**：登录仍由 WebView 主导；纯 API 登录仍是备选；
会话 Cookie 仍由 `WebCookieManager` 承载（漫游响应下发的 Cookie 正是经它落盘并复用的）。

## 理由

- **票据路径就是浏览器原本要做的那一步**：不需要密码、不需要重新认证、
  不依赖设备是否已被登记为信任浏览器——而后者在真实账号上恰恰不可靠（见背景 2）。
- **实测通过**：真实账号（含多因子认证）在校园网下完成登录，日志
  `收尾：漫游地址 参数=[ticket] ticket长度=36` → `漫游票据建会话成功（复用网页会话，未重新登录）`
  → `建会话方式=漫游票据`；杀进程重开后 `沿用已持久化的会话`。
- **保留兜底不损失什么**：兜底只在首选不可用时才跑，且它覆盖了"未启用多因子认证的账号"
  与静默恢复等场景。

## 后果

- **正面**：登录对"设备未被信任"的账号也能走通；少一次密码加密与一次校验请求；
  排查路径清晰（`建会话方式` 直接给出结论）。
- **负面**：依赖 `onLoadIntercept` 能拿到**带票据的**漫游 URL。若校方改为不带票据导航，
  或票据改用其他传递方式，首选路径失效——此时会自动落到兜底并在日志中标明。
- **后续约束**：票据是**一次性凭据**，绝不进日志（只记长度）；首选路径不清 Cookie，
  不要在它之前清理会话，否则可能破坏票据校验所需的上下文。

## 备选方案

- **原样重放页面表单体**：ADR-0008 初稿的读法，实测拿不到工单（背景 1）。**否决**。
- **只做"带设备信任标识重新登录"**：对未登记信任浏览器的多因子认证账号原理上不可行
  （背景 2）。**否决**（保留为兜底）。
- **不取消导航，让 WebView 自己走完漫游再接管会话**：可行但会把网络学堂的网页界面
  呈现给用户，且依赖 WebView 与 API 侧确实共用 Cookie 存储；相较之下票据路径
  改动更小、对用户可见行为更干净。**备选**（若首选路径失效，可改用此方案）。
