# ADR-0010：为完成设备信任登记，注入脚本就地抬高页面的存储配额读数

## 状态

已接受（2026-09-27 用户确认保留该行为）
**但"它是否必需"尚未验证**——见「后果」里的对照实验，该实验未做之前不得把必要性当结论引用。

## 背景

ADR-0008 决定登录由 WebView 主导，并允许在 `id.tsinghua.edu.cn` 上注入脚本；
`docs/SECURITY.md` §3 当时把注入**允许做的事穷举为四件**（预填学号密码、页面询问时答"信任此浏览器"
并写入设备指纹、回传提交时的表单体、回报结构异常），并写「任何 WebView 都不得注入脚本或改变页面行为」。

而实现里 `resources/rawfile/sso_inject.js` 另有**第五件事**：`patchIncognitoDetection()`
（脚本 `:536-565`，经 `:642` 在 `beforePageScripts()` 里无条件执行）就地把
`navigator.storage.estimate` 与 `navigator.webkitTemporaryStorage.queryUsageAndQuota`
的读数抬到 64GB，好让校方二次认证页所用的第三方库 `detectIncognito` v1.4.1
**不要**判定"隐私或匿名模式"。

脚本注释给出的理由是：该库在移动端 WebView 上会把"存储配额偏小"误当隐私模式
（触屏分支 `estimate().quota < 2GB`；Chrome 分支配额 `< 2×JS 堆上限`），于是页面只提供"否"，
设备信任登记登记不上，每次登录都要重新二次验证；并称实测登记请求返回 `msg:"否"`，
而应用侧 `isIncognitoMode()` 为 `false`。

**但这条理由与项目自己的实测记录冲突。** `docs/specs/auth-login.md` §11.2 记录真实账号运行时
「保存信任浏览器」返回 **`status=200 result=success`**——登记**成功了**；那句"隐私或匿名模式"
是页面弹的**客户端提示**，**没有**阻止登记；并据此把 §9.2 ② 的"存储不可用导致判定隐私模式"推断**证否**。

## 决策

**保留该行为，并把它正式纳入授权范围**（而不是让它继续处于"实现了但没文档"的状态）：

1. 允许注入脚本在 `id.tsinghua.edu.cn` 上就地把上述**两个配额查询方法**的读数抬到阈值之上；
2. 该行为写入 `SECURITY.md` §3 的允许清单，作为**第五件事**，并引用本 ADR；
3. 本 ADR 同时记录"必要性未验证"这一事实与判定实验（见「后果」）。

### 硬性边界

- **仅 `id.tsinghua.edu.cn`**（靠 `scriptRules` 限定，与其余注入行为同一道闸）；
- **只就地替换那两个方法**，不替换 `navigator.storage` / `webkitTemporaryStorage` 对象本身
  （页面若用到其他成员如 `persist` / `getDirectory`，换对象会缺方法）；
- **抬不动就静默退让**（`try/catch` 后让原判据生效，不抛错、不阻断登录）；
- **不代填、不代答验证码**（ADR-0008 的约束不变）；是否"信任此浏览器"仍按用户意图作答，
  用户仍可在页面上选择拒绝；
- 其他 WebView（如后续的富文本正文渲染）**不注入任何脚本**。

## 理由

- 被改写的读数是**客户端启发式**（库用它判断"能否用扩展存储"），不是安全控制；
  它不参与凭据校验，也不决定服务端是否认可认证结果。
- **在必要性未定的情况下，保留是较低风险的一侧**：去掉它若确实必要，代价是多因子账号
  每次登录都要重新二次验证（持续摩擦，且用户难以归因）；保留它若其实不必要，代价是一个
  替代读数与两个被覆盖的方法（行为局部、可逆）。
- 因此这里的取舍是"先保留、再实验定论"，而不是"先删掉、再等用户报障"。

## 后果

- **正面（条件性）**：若该 patch 确实必要，则设备信任登记可以完成，用户免去每次登录的二次验证。
- **负面 / 未决（重要）**：**必要性未经验证**。ADR-0008 时代的记载（登记返回 `msg:"否"`）与
  `auth-login.md` §11.2 的记载（登记 `result=success`）互相冲突；而 §11.2 那次观测是在
  **该 patch 已在位**的前提下做的，因此它**既不能证明 patch 必要，也不能证否它**。
  两处文档在当前状态下都不可作为结论。
  **判定实验（未做）**：临时移除 `patchIncognitoDetection()` 的调用 → 用真实账号完成一次登录 →
  观察两件事：①「保存信任浏览器」的服务端 `result` 是否仍为 `success`；② 下一次登录是否仍被要求验证码。
  若两项都无变化，则该 patch 与其在脚本里的理由**都应删除**（并在本轮把它记入 CHANGELOG 的用户可见变更）。
- **维护负担**：依赖 `detectIncognito` 的判据形态与阈值（64GB 按实测 `jsHeapSizeLimit≈2.19GB` 的
  2 倍推算，故必须"明显大于"）；库升级或校方改用别的判据即失效，需重测并相应调整常量或删除。
- **可观测性**：脚本已回报 `ENV_PROBE 隐私判定输入 …`（分支判据、`estimate`/`webkitTemporaryStorage`
  是否存在、`jsHeapSizeLimit`）与 `页面文案 隐私提示=有/无`，上述实验只需读这两条日志即可判定。
  > 注：这两条回报本身的内容边界见代码审查 R-07（页面内容进 public 日志的脱敏问题），属独立整改项。

## 备选方案

- **移除 patch、接受那个"化妆品级"告警**：若 §11.2 的结论成立，这是更干净的选择（不改变页面行为）。
  但当前证据不足以判定，故不采用——**列为上述实验的预期结论之一**。
- **在登录失败时引导用户处理"信任浏览器"名额**：`msg:"否"` 与名额已满不是同一件事，
  且引导解决不了该客户端判据本身。**否决**（仅对"名额已满"有效，那条已有独立引导）。
- **让 WebView 以"非隐私模式"启动**：应用侧 `isIncognitoMode()` 实测本就是 `false`，
  问题不在 WebView 的隐私模式开关。**不适用**。
- **改走纯 API 直连绕过此页**：ADR-0008 已否决——多因子验证码只能由用户在真实页面输入。**否决**。
