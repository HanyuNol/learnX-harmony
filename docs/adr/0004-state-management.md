# ADR-0004：状态管理采用 ArkUI 原生状态 + 单一应用级 Store

## 状态
已接受

## 背景

上游使用 Redux（`@reduxjs/toolkit`）+ `redux-thunk` + `redux-persist`，含 9 个 reducer 切片（auth、semesters、notices、assignments、files、courses、settings、user、root），并有选择的持久化（`blacklist: ['auth', 'settings']`）。

ArkTS 侧没有 Redux 的等价库，且本项目禁止引入 RN/JS 生态依赖。需要为 ArkTS 选定状态方案，覆盖两类需求：

1. **页面内状态**：列表数据、加载中/错误态、筛选条件——生命周期与页面一致。
2. **跨页面共享状态**：登录态、当前学期、设置、各维度缓存——需在多个页面间共享并部分持久化。

## 决策

分两层，均用 ArkUI 原生能力，不引入第三方状态库：

1. **页面内状态**：用 ArkUI 状态装饰器（`@State` / `@Prop` / `@Link` 等）在页面与组件内管理。
2. **跨页面共享状态**：用**单一应用级 Store**（应用级单例 + 观察者订阅）承载领域状态，替代 Redux 的角色；页面通过订阅获取变更。**不逐切片照搬 Redux 结构**，按领域拆分为少量状态组（认证 / 学期 / 内容缓存 / 设置）。
3. **持久化分流**：凭据走系统加密存储（见 `SECURITY.md`）；偏好设置走系统首选项；列表缓存走本地缓存。三者均不与状态 Store 直接耦合，经 `storage/` 统一访问。

## 理由

- ArkUI 的状态装饰器足以覆盖页面内场景，无需抽象。
- 跨页面共享状态用"单例 + 订阅"即可满足本项目规模（约 26 个 FR、数种领域实体），无需引入 reducer/action/middleware 全套范式——那是为大型前端团队协作设计的，对本项目是过度工程（违反架构不变量 §2 简单优先）。
- 不照搬 Redux 切片结构：上游的 9 切片部分是为 redux-persist 的选择性持久化服务；本项目持久化由 `storage/` 显式处理，切片边界失去存在理由。
- 订阅式共享状态便于 ArkUI 精确刷新，避免全局重绘。

## 后果

- **正面**：零第三方状态依赖；概念少、上手快；持久化责任集中可审计（利于凭据安全要求）。
- **负面**：没有 Redux DevTools 式的调试体验；Store 的订阅与释放需手工管理，**忘记反订阅会造成内存泄漏**——列入高风险区（见 `testing-and-quality.md` §2）。
- **后续约束**：若共享状态规模增长到单例难以维护，需**先写新 ADR 取代本条**，不得在代码里私自分叉出第二个 Store。

## 备选方案

- **照搬 Redux 范式（自研 reducer/dispatch）**：概念成本高，对本项目规模是过度设计。
- **只用 AppStorage / PersistentStorage**：面向简单键值，不适合承载带业务编排的领域状态与列表缓存。
- **引入第三方 ArkTS 状态库**：与"禁引入 JS 生态依赖""简单优先"两条不变量冲突，且鸿蒙生态此类库成熟度与长期维护性不足。
