# ADR-0006：接受"仅校园网可达"前提，不自建中转服务

## 状态
已接受

## 背景

网络学堂（`learn.tsinghua.edu.cn`）与统一身份认证（`id.tsinghua.edu.cn`）**仅在校园网或校方 VPN 内可达**。这带来三个具体影响：

1. 大量用户在校外，应用无法直连——这是产品固有约束，不是缺陷。
2. 开发与验证都需要校园网环境。其中**端到端验收（真实账号、真实数据）必须在校园网内完成**（见 PRD §6 第 2 项）。
3. 上游额外接入了一个第三方非官方服务 `api.tsinghua.app`（CourseX 课程信息共享，GraphQL）用于 FR-27，其可用性与合规性不受本项目控制。

存在一条看似省事的路线：自建一个中转/代理服务，把校方接口包装成公网可达。

## 决策

1. **不自建中转、代理或缓存服务**。应用直连校方接口，网络前提由用户自行满足（校园网或校方 VPN）。
2. **把"网络不可达"作为常态设计**：网络不可达、认证失效、接口语义变更、解析失败**四类错误分开归类与呈现**，不得把服务端/网络问题误报为应用缺陷（对应 NFR-NET）。
3. **FR-27（课程信息共享）降级为 P3 且可放弃**：若 `api.tsinghua.app` 不可用或不适宜接入，该 FR 直接不做，不自行实现替代服务。

## 理由

- **中转服务会引入本项目无法承担的责任**：代理意味着要持有或转发用户的登录凭据，把"用户 → 校方"的信任关系变成"用户 → 第三方中转 → 校方"。这在安全（见 `SECURITY.md` 信任模型）、合规与运维成本上都不成立，且与"不做服务端"的非目标直接冲突。
- **校方 VPN 已是既有解法**，用户群体本就有账号；应用重复提供一条能力更弱、责任更重的通道没有价值。
- **四类错误分开归类**是低成本、高收益的设计：它让"校外打不开"这件事可被正确理解和沟通，而不是被当成 bug 反复排查。
- 第三方非官方服务不应成为产品关键路径，因此排到 P3 且明确可放弃。

## 后果

- **正面**：不承担凭据转发的信任责任；无服务端运维成本；错误语义清晰。
- **负面**：校外用户在无 VPN 时**完全无法使用**（这是产品边界，不是待修缺陷）；开发者在家调试受限。
- **后续约束**：
  - 任何时候**不得**为"让校外也能用"而引入中转、镜像或第三方代理。
  - 若确需改变此边界（例如接入校方官方新接口），**必须先写新 ADR 取代本条**。
  - 端到端验收项在无校园网时**不得**以"测试通过"替代，须如实标注为未覆盖。

## 备选方案

- **自建中转服务**：与"不做服务端"非目标冲突；引入凭据托管的信任与合规问题；运维成本与风险远超收益。
- **应用内置校方 VPN 客户端**：范围爆炸，且涉及校方认证系统的集成授权，不在本项目范畴。
- **仅保证校内可用但不做错误归类**：会让"校外不可达"持续被误报为应用故障，是本 ADR 主要要避免的结果。
