# ADR-0008：登录改为 WebView（ArkWeb）主导，纯 API 登录降为备选

## 状态
已接受

## 背景

FR-01 原设计为**纯 API 七步登录**（抓 SM2 公钥 → 加密提交凭据 → 换漫游工单 → 漫游建会话 → 取 CSRF）。
该设计已实现并通过静态检查与单元测试，但在**真实账号**上不可用：

- 实测：登录校验返回的是标题为「**二次认证**」的页面（约 1661 字节），而非带漫游工单的成功页。
  此时 Cookie 正常（`cookieLen=52`）、网络可达、编码格式（urlencoded 与 multipart）经对照实验
  证明服务端都接受——**失败与网络、Cookie、编码无关**。
- 上游 `robertying/learnX` 的登录主路径**本来就是 WebView**（`Login.tsx` 按登录必跳转 `SSO` 页），
  并在 `src/assets/translations/zh.ts` 的提示文案中明确了交互：
  「请在即将打开的网页中完成登录」「多因子认证 - 信任浏览器数量」。
  本项目初版把这条路径当作可选的 P2 功能（FR-02），是**范围误判**。

关键事实：**多因子认证的验证码必须由用户在真实页面上输入**。纯 API 流程**没有任何位置**能承载
这一步，因此对本校启用多因子认证的账号（含本项目验收账号）从原理上不可用。

## 决策

**登录主路径改为 WebView（ArkWeb）主导**，流程：

1. 应用内打开真实认证页 `https://id.tsinghua.edu.cn/do/off/ui/auth/login/form/...`，
   以干净会话起步（不带既有 Cookie）。
2. 注入 JS：预填学号与密码（`input#i_user` / `input#i_pass`，置只读），供用户确认。
3. **用户在该页面内完成登录**——包括输入多因子认证验证码；页面若询问"是否信任此浏览器"，
   由注入脚本写入应用设备指纹并答"是"。应用不介入、不代填验证码。
4. WebView 自行完成认证与漫游。当导航目标命中网络学堂漫游地址时，应用收尾。
5. 注入脚本在表单提交时抓取**完整表单体**（含服务端页面生成的 `fingerPrint` /
   `fingerGenPrint` / `fingerGenPrint3`）并回传应用。
6. 应用以抓到的表单数据执行既有 API 登录流程以建立会话与 CSRF，后续请求照旧。

**纯 API 登录保留**，但降级为"未启用多因子认证的账号"的备选路径，不再是默认路径。

**Cookie 改由 `webview.WebCookieManager` 统一承载**（进程级、同步读写、`saveCookieAsync` 可持久化），
替代本项目自写的内存 `CookieJar`：WebView 与 API 请求由此共享同一份会话，且冷启动后会话可存活。

## 理由

- **验证码只能在真实页面里输入**——这是纯 API 方案不可逾越的硬约束，不是实现难度问题。
- 上游已验证该交互可行，且其提示文案说明了设备信任名单的运维细节，风险可控。
- 设备指纹与信任登记由页面的 JS 生成、经 WebView 抓取，**API 直连无法获得这些值**
  （它们是二次认证的设备信任标识）。走 WebView 是获取它们的唯一途径。
- 与用户在资源受限场景下的直觉一致：**把网页当浏览器用**，认证逻辑留在校方页面内，
  应用不必复刻其多因子认证协议（复刻既有安全风险，也会随校方改版失效）。

## 后果

- **正面**：启用多因子认证的账号可用（本校主力人群）；不必复刻与维护校方多因子认证协议；
  WebView 与 API 共享 Cookie，会话一致性更好，冷启动可保持登录。
- **负面**：
  - 登录不再是"填完即登"，多一步页面交互，且**依赖校方页面结构**（表单选择器、提交事件）。
  - 引入 `ArkWeb` 依赖与一个承载页面的登录界面，测试面扩大（WebView 行为难以在宿主侧单测）。
  - 需要处理"信任浏览器数量已达上限"这一可预见失败，并给出可操作引导。
- **后续约束**：
  - 设备指纹**必须持久化复用**——每次登录换新指纹会迅速占满信任浏览器名额。
  - 注入脚本依赖的页面选择器与接口路径（如 `/b/doubleAuth/personal/saveFinger`）一旦变更即失效，
    必须与"接口语义变更"分类一样可快速定位，并集中在一处维护。

## 备选方案

- **纯 API 登录 + 自行实现多因子认证**：需复刻校方 OTP 协议（含验证码下发与校验），
  既有安全责任，又随校方改版失效；且验证码仍需用户输入，绕不过交互。**否决**。
- **把纯 API 登录作为唯一路径、要求用户关闭多因子认证**：把成本转嫁给用户，
  且与校方安全要求相悖。**否决**。
- **WebView 套壳整个网络学堂 Web UI**：开发量最小，但丢失原生列表、离线、通知、日历等全部本地能力，
  与产品目标不符（ADR-0001 已否决过同类方案）。
