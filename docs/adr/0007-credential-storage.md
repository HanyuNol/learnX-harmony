# ADR-0007：凭据与会话存储采用关键资产存储服务

## 状态
已接受（待随 FR-01/03/04 的 spec 一并审核）

## 背景

FR-03 要求凭据（学号、密码）与设备指纹在设备上**加密存储**，且 `SECURITY.md` 已定下红线：凭据只能存在于系统加密能力中，不得明文落盘、不得入日志、不得入库。

需要选定"存哪里、怎么加密"。候选：

1. **关键资产存储服务**（`@ohos.security.asset`，Asset Store Kit）—— 面向凭据类数据设计的系统服务。
2. **首选项**（`@ohos.data.preferences`）+ 自行加密（cryptoFramework 做 AES 加解密）。
3. **首选项明文**。
4. **不持久化**，每次启动重新登录。

## 决策

采用**关键资产存储服务**（`@ohos.security.asset`）存储凭据与设备指纹；由 `storage/credentialStore.ets` 作为**唯一读写入口**。

## 理由

- 该服务正是为凭据类数据设计的：加密与访问控制由系统负责，应用不接触密钥。
- 方案 2 存在**密钥托管的循环问题**：自行加密就需要一把密钥，而"那把密钥又存在哪里"回到同一个问题；若密钥硬编码在应用内则等于没加密。为绕开它还要引入派生密钥等自研设计，出错面远大于收益。
- 自研加密是经典的自伤点（填充、IV 复用、模式选择都可能出错），而这里保护的是用户在校统一身份认证的密码，代价极高。**不自己造这个轮子。**
- 方案 3 直接违反 `SECURITY.md` 与 NFR-SEC。
- 方案 4 违反 FR-01"持久化登录态"的要求，且每次输入密码的体验不可接受。

## 后果

- **正面**：凭据加密与访问控制交由系统，符合项目安全红线；写入/读取/清除集中在一处，便于审计。
- **负面**：
  - 该服务的行为受设备状态影响（例如某些安全属性下可能要求设备已解锁），需要在实现时确认失败分支并归入"认证失败"给出可理解提示。
  - 需要处理"资产不存在"（首次运行）与"资产存在但读取失败"两种情形的区别，不能混为一谈。
- **后续约束**：
  - 任何模块**不得**直接调用该 Kit，必须经 `credentialStore`。
  - 登出**必须**清除全部凭据与指纹。
  - 引入新的凭据类数据时，同样走该服务，不得退化为首选项或明文文件。

## 备选方案

- **首选项 + 自研加密**：密钥托管循环问题无干净解，且自研加密实现在密码这类高价值数据上不可接受。
- **首选项明文**：违反安全红线，直接否决。
- **不持久化**：违反 FR-01，用户体验不可接受。
- **依赖应用沙箱隔离而不额外加密**：沙箱并非加密，越狱/提权/备份导出场景下凭据即明文，不满足 FR-03 的"加密存储"表述。
