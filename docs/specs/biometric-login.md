# 功能规格：生物识别快速登录（指纹 / 人脸解锁已保存的凭据）

> 状态：开发中　·　关联 PRD：FR-24　·　分支：main
> 上游 `robertying/learnX` **没有**这项能力（发到应用商店的版本靠系统锁屏就够了）。

## 1. 背景与目标

现在只要用户勾过「记住密码」，应用**启动时不做任何验证**就静默恢复登录态
（`authRepository.tryRestoreSession` → `client.restoreSession(credentials)`）。
手机解锁着放在桌上时，任何人拿起来点开应用就是已登录状态。

FR-24 补上这道闸：**用已保存凭据自动登录之前，先要一次生物识别**（指纹/人脸）。
这不是"再加一个密码框"，而是把"开机即已登录"换成"开机按一下指纹"。

## 2. 需求（要什么）

**范围内**：

1. **有凭据 + 设备可生物识别 → 先验证再恢复**：验证通过才用已保存凭据恢复登录态；
2. **验证未通过（取消/失败）→ 不恢复**，落到登录页，用户用密码登录（**回退路线必须成立**）；
3. **设备不可生物识别（没录入/不支持）→ 照旧静默恢复**：绝不能因为"没有指纹"
   就把用户挡在登录页——那台设备上原本就没有这个风险，凭空加一道闸是制造故障；
4. **失败不谎报、不崩**：系统侧异常一律按"未通过"处理（不恢复），并只记日志；
5. **凭据不落地任何新地方**：生物识别只是**闸门**，凭据仍只由 `storage.CredentialStore` 读写；
   不把凭据、也不把任何派生值交给生物识别接口（§3.3 第 4 条）。

**不做（范围外）**：

- **不做"用生物识别替代密码去登录"**（即拿指纹换一个 token）：本 FR 不产出任何新凭据形态，
  纯粹是"何时允许自动恢复"的闸门。少了它就不需要发明新的凭据存储；
- **不做设置开关**：设备不支持时自动退回原行为（第 3 条），所以"不想用"的用户
  只是"多按一次指纹"或"直接用密码登录"，不需要一个额外的开关来关掉安全兜底；
- **不订阅/展示生物识别的错误码给用户**：取消（`CANCELED`）与失败（`FAIL`）对用户是同一件事
  （没通过 → 用密码），细分只在日志里；
- **不做人脸/指纹的优先级设置**：交给系统（`authType` 传两类，由系统决定弹哪种）。

## 3. 设计（怎么做）

### 3.1 上游事实（对照基线）

| 事实 | 出处 |
|---|---|
| 上游无生物识别，也无"启动时验证"这一步；登录态由保存的凭据直接恢复 | 全库检索无相关实现 |

> 与上游的**有意不同**：本项目把"已保存凭据"视为敏感物，多一道本地闸门。

### 3.2 模块与文件

| 层 | 文件 | 职责 |
|---|---|---|
| `common` | `biometricGate.ets`（新） | **纯逻辑**：由"有没有凭据 / 能不能生物识别 / 验没通过"决定处置（可穷举测试） |
| `native` | `biometricAdapter.ets`（新） | `@kit.UserAuthenticationKit` 的唯一出口：可用性查询 + 发起验证 |
| `repository` | `authRepository.ets`（改） | `tryRestoreSession` 先过闸门，按处置决定要不要恢复 |

### 3.3 关键规则

1. **闸门放在 `tryRestoreSession` 里**，而不是某个页面的 `aboutToAppear`：它是"能不能用这些凭据"
   的判据，属于恢复流程本身；放页面会出现"哪个页面先起来谁说了算"。
2. **三种处置由纯函数给出**（`decideRestore`）：

   | 有凭据 | 可生物识别 | 验证通过 | 处置 |
   |---|---|---|---|
   | 否 | — | — | `none`：不恢复（首次运行/没勾记住密码） |
   | 是 | 否 | — | `silent`：**照旧**静默恢复（设备没这个能力） |
   | 是 | 是 | 是 | `unlocked`：恢复 |
   | 是 | 是 | 否 | `none`：**不恢复**，回退密码登录 |

   这张表就是本 FR 的全部行为，故做成纯函数并逐行写用例——**尤其"不可用要照旧恢复"那行**，
   它写错的后果是"老设备上所有人登不进去"。
3. **可用性查询取"任一生物识别类型可用"**：`getAvailableStatus` 按类型抛错
   （`12500005 类型不支持` / `12500010 未录入`），指纹与人脸各查一次，**两者都不可用**才算不可用。
4. **凭据不进生物识别接口**：`AuthParam.challenge` 传空数组、`authType` 只传类型、
   `authTrustLevel` 传 `ATL2`（普通应用解锁这一档）。生物识别只回一个"成/不成"，
   **不返回任何可用于登录的材料**——凭据依旧在闸门通过之后由 `CredentialStore` 读。
5. **系统异常按"未通过"处理**：`getUserAuthInstance`/`start` 抛错时不得让恢复流程崩溃，
   一律走 `none`（回退密码），并把错误码只记进日志。
6. **必须申明 `ohos.permission.ACCESS_BIOMETRIC`**（`module.json5`）。这是本轮**实测抓到的近失**：
   该权限是 **`system_grant` + `normal` 级**（SDL 的 `PermissionDefinitions.json` 里写明的），
   **申明即生效、不弹授权框**；但**不申明就会拿到 `201 权限拒绝`**——
   于是每台设备看起来都"不支持生物识别"，闸门永远不触发，**功能静默失效、且日志看着一切正常**。
   申明后同一台模拟器上的返回码变成 `12500010`（未录入凭据），即真正的能力答复。

## 5. 验收标准

**自动化（已过）**：

1. `decideRestore` 4 组用例（§3.3 第 2 条的表，含"无凭据"与"不可用要静默恢复"两行）；
2. 静态门：`check arkts` 主 101 / 测试 28 文件 0 error、`check lint` 0 error、`build` 成功、
   **297 例单测 0 失败**。

**设备验收（模拟器 learnx / 真实账号，2026-09-29）**：

3. ✅ **无生物识别的设备照旧能用**（本 FR 最要紧的一条，因为做错就是把所有老设备挡在门外）：
   冷启动日志为

   ```
   [biometric] 生物识别不可用 type=4 code=12500010      ← 指纹：未录入
   [biometric] 生物识别不可用 type=2 code=12500010      ← 人脸：未录入
   [authRepository] 设备不可生物识别，按原行为静默恢复
   [authRepository] 已恢复登录态                        ← 1 秒后
   ```

   随后 `startupSync` 预载、通知/文件加载正常，节点树确认停在主界面（通知列表已出数据）；
4. ✅ **权限申明生效**（§3.3 第 6 条那次近失的回归）：申明前同一台模拟器返回 `201 权限拒绝`，
   申明后返回 `12500010`——即"这台设备没录入指纹/人脸"，是真正的能力答复。
5. ⚠️ **用户真机（有指纹/人脸）**：启动时弹系统验证；按指纹 → 进应用；取消 → 停在登录页
   （用户名已回填）、用密码能登进去。**这一条需要用户的手机**，模拟器没有该硬件，无法构造。

> **`devecocli run` 末尾的 `Smoke` 判定不可靠（本轮实测两次误报）**：一次因该次启动要走
> "会话过期 → 用凭据重新登录"（多花约 2 秒）判 `FAIL_BLANK`；一次判 `FAIL_CRASH`，
> 而查下来是它读到了**六天前**的一条 `appfreeze` 记录（`appfreeze-…-20260927113148`）。
> 两次应用本身都正常起来了（hilog + 节点树可证）。故**验收以 hilog 与节点树为准**，
> `Smoke` 只能当提示。这条已写进 `OPERATIONS.md` §7.5。

## 6. 风险 / 待定

| 项 | 说明 | 处置 |
|---|---|---|
| 真机上的验证弹窗 | 模拟器无生物识别硬件，第 4 条验收做不了 | 如实标未验，等用户真机；代码侧只保证"不可用不挡人"这条已验 |
| 每次启动都要按一次 | 有指纹的设备上，每次冷启动都会弹验证 | 这是本 FR 的意图（与微信/银行类一致）；若用户觉得烦，可加设置开关，属后续增量 |
| `ATL2` 这一档是否够/过严 | 档位越低越容易被系统判定"可用"，越高越严（ATL4 要锁屏密码级别） | 取 ATL2（普通应用解锁常用档）；若真机上报 `12500006 信任等级不支持`，改档位即可，日志里能看出来 |
