# 功能规格：通知公告（列表 · 详情 · 已读/未读筛选）

> 状态：待审核　·　关联 PRD：FR-06（与 FR-12 的边界见 §2）　·　分支：main
> 接口语义基线：上游 `thu-learn-lib@4.0.0` 的 `src/urls.ts` / `src/index.ts`；
> 交互参照上游 `robertying/learnX` 的 `data/actions|notices.ts`、`screens/Notices.tsx`、
> `screens/NoticeDetail.tsx`、`components/NoticeCard.tsx`。**只取语义，不移植代码**（ADR-0001）。

## 1. 背景与目标

通知是四个内容维度里第一个落地的。它与课程（FR-09，已交付）的关系是硬依赖：
**通知按课程取**——`getNotificationList(courseID, ...)` 的请求体里只有 `wlkcid`，
没有学期参数；RN 侧从课程状态派生 courseIds 再扇出（`Notices.tsx:21-24,38`）。

因此本 FR 也是**第一个会引入并发请求**的地方，必须先解决 `ARCHITECTURE.md` §5.6 记的
**R-03**（`LearnClient` 用单个可变字段 `pendingUrl` 判断 `Set-Cookie` 属于哪个主机，
并发下会把 Cookie 写到错误主机，而症状会被下游归成"密码错误"）。

## 2. 需求（要什么）

**范围内**：

1. 通知列表：聚合**当前学期所有课程**的通知，按发布时间倒序；
2. 列表项展示：课程名、标题、正文摘要（去标签、两行截断）、发布者、发布时间（相对时间）、
   未读标记、重要标记、有附件标记（对齐上游 `NoticeCard` 的这些字段）；
3. 通知详情：标题、发布者、发布时间、正文（**先按纯文本呈现**，见下）、附件名；
4. **已读/未读筛选**（FR-06 那一行里明确要求的）；
5. 三态齐备（加载 / 空 / 错误+重试）；下拉或按钮刷新；
6. 从课程详情页的通知页签进入时，只列该课程的通知（上游 `getNoticesForCourse` 的对应能力）。

**不做（属其他 FR，或本批不做）**：

- **正文富文本渲染（HTML/公式）**：属 **FR-22**（P2）。本 FR 详情页把正文按**纯文本**呈现
  （复用 `parse.stripTags`）。安全上也更稳：SECURITY §3 要求"按白名单清洗、不得整体信任服务端 HTML"，
  那件事在 FR-22 一并做；现在**更不该**把未清洗的 HTML 塞进 WebView；
- 附件点开：上游点附件名跳"文件详情"（FR-08）。本批**只显示附件名**，跳转等 FR-08；
- 收藏 / 归档（上游有 `SET_FAV_NOTICE` / `SET_ARCHIVE_NOTICES`）：这两个筛选属 FR-12 的通用筛选范畴，
  本批不做；
- **磁盘缓存**：`ARCHITECTURE.md` §5.3 要求"网络失败时退让为展示上次缓存 + 明确提示"。
  上游靠 redux-persist 落盘。本批**只做内存态**（重启后重新拉），磁盘缓存与按学期分区
  作为独立任务处理（§6 已登记）——否则本 FR 会膨胀成"顺手把同步与缓存机制做完"；
- 全局搜索（FR-17）、后台同步（FR-25）、通知提醒（FR-18）。

### 3.3 关键规则

1. **并发上限（本 FR 的新决策）**：按课程扇出时**限制同时在飞的请求数**（拟 4）。
   上游对全部课程 `Promise.all`、每课再并行两次——12 门课会同时飞 24 个请求。
   在移动端这对网络与内存都不友好，且**正是 R-03 的触发场景**。上限值属工程判断，
   实现时以"不出现超时/失败率上升"为准，并把实测结论记回本 spec。
2. **部分失败策略**：某门课拉失败时**不整页失败**——保留拿到的通知，记 WARN，并在列表顶部
   给一条"部分课程的通知未能加载"的提示（文案键）。全部失败才进错误态。
   理由：上游是全量 `Promise.all`，一门失败就整体失败；12 门课里坏一门导致整页空白，
   体验与排障都差。这条与上游不一致，**是本项目的刻意选择**。
3. **失败归类**：非 2xx 走 `fromStatusCode`；结构不符 → 解析失败；网络错误由 `normalize` 归类。
4. **筛选（与 FR-12 的边界）**：本 FR 只做**通知维度**的"全部 / 未读"两个选项，
   判据为纯函数 `filterNotices(items, filter)`；**不做**通用筛选框架、不做"记住上次选中"、
   不做收藏/归档。FR-12 落地时把这里的选择器与判据提升为四维度通用（届时改 `FilterList` 那一层，
   本 FR 的纯函数可原样复用）。
5. **正文纯文本**：`stripTags` 后呈现，**不做 HTML 渲染**（FR-22）；换行按原样保留，
   便于阅读。
6. **时间显示**：列表项显示相对时间（如"3 天前"）。时区/格式随系统——用什么 API 见 §6 待定，
   实现时先确认（不臆测）。
7. **未读标记**：`hasRead` 只读服务端。打开详情时按上游发一次"已读"请求（`getWithAuth`），
   **失败只记日志**；成功后**乐观地**把该条本地标为已读（下次刷新以服务端为准）。
   > 与上游的差别：上游不动本地状态，于是"刚点开过的通知仍显示未读"直到刷新。
   > 这个乐观更新是本项目的刻意选择——但**如果服务端其实没记成功**，界面会短暂说已读；
   > 下次刷新会纠正。若你认为该严格对齐上游（不动本地状态），告诉我改回。
8. **课程为空**：不发请求（沿用 FR-09 的守卫），呈现空态而非错误态。
9. **取数范围恒为整个学期，课程范围在展示层过滤**（对齐上游 `CourseDetail.tsx:226-243`）。
   这条是实测踩坑后补的：曾让"通知标签"与"课程详情页签"各按自己的范围去取数，
   而 store 是应用级单例、只有一份列表，于是后请求的一方把列表换掉，另一处显示成别人的内容。

## 5. 验收标准

**自动化可验证（单元测试，不依赖设备）**：

1. 响应解析：合法响应 → `Notice[]`（Base64 正文解出、HTML 实体解出、缺字段退让）；
   非数组 / 坏 JSON / 非 success → 抛出；空数组是合法结果。
2. 两次请求（未过期 + 已过期）合并后**按发布时间倒序**，同一时间按 id 倒序。
3. 摘要：去标签、压缩空白、截断长度（按字符而非字节，中文不能被切坏）。
4. 未读筛选：`filterNotices(items, 'unread')` 只留 `hasRead === false`；`'all'` 原样返回。
5. 扇出编排的纯部分：给定"每门课的结果或失败"，产出"合并后的通知 + 失败的课程数"
   （把部分失败策略做成纯函数，便于穷举：全成功 / 部分失败 / 全失败）。
6. 静态门：`check arkts`（主 + 测试显式传路径）、`check lint` 零错误；`build` 成功；
   `check-l10n` 键集合一致。

**设备验收（模拟器/真机，已登录会话可用）**：

7. 通知标签加载出**当前学期多门课的通知**，按时间倒序；列表项含课程名/标题/摘要/发布者/时间/未读标记；
8. 点一条进详情：标题、发布者、时间、**纯文本正文**、附件名（有附件时）；
9. 筛选切到"未读"：只剩未读项；切回"全部"恢复；
10. **R-03 回归**：扇出并发下通知能正常加载（不出现整页失败），且会话 Cookie 未被写错主机
    （判据：并发加载后仍能正常取课程/学期，不需要重新登录）；
11. 失败面：断网或会话失效时呈错误态 +「重试」；部分课程失败时顶部有提示且已拿到的通知仍显示。

> 需要已登录会话。**第 10 项是本 FR 特有的关键项**：它同时验证 R-03 的修复。

**需用户确认**：PRD §6 第 2 项里"浏览通知"这一环节。

### 5.2 实现期间发现并修掉的四个缺陷（都只有真机才能暴露）

1. **POST 全缺 CSRF 令牌 → 403**：上游对每个请求都注入 `_csrf`，本项目原先只在 GET 注入；
   通知一条都取不到，**登出同样受影响**。
2. **POST 的 `Accept: text/html` → 406**：这些端点返回 JSON，改为 `*/*`。
3. **课程未预加载 → 通知一条都取不到**：通知按课程扇出，而课程原先只在打开"课程"标签时才加载；
   现在 `Main` 在学期就绪后顺带把课程拉起来。
4. **通知标签与课程详情页签互相混**：两者用不同取数范围抢同一份应用级列表（用户实测报的），
   已按上游改为"列表只存整学期、课程范围展示层过滤"。
