## 1. 背景与目标

P1 的地基。所有其余 FR（学期、通知、作业、文件、课程）都必须先有"能认证、能发请求"的前提，因此本功能先做。

要解决的问题：在 HarmonyOS 上复刻 learnX 的网络学堂认证链——用学号密码换到会话，并让后续请求自动携带会话与 CSRF 令牌；同时把凭据安全地存在设备上，让用户不必每次登录。

**三个 FR 合成一个 spec 的原因**：它们共用同一组模块（`network` / `storage` / `repository` / `model`），无法单独交付。

## 2. 需求（要什么）

- **FR-01**：以学号 + 密码登录网络学堂，登录成功后持久化会话与凭据，下次启动免登录。
- **FR-03**：凭据（学号、密码）与设备指纹必须以系统加密能力存储；不落明文、不入日志、不进代码、不入库。
- **FR-04**：应用启动与每次请求前校验登录态；服务端判定会话失效时给出明确提示并引导重新登录，不静默失败、不白屏。

**范围内**：

- 账号密码登录（含上游的 SM2 加密与漫游工单流程）
- CSRF 令牌的获取与注入
- 会话内的 Cookie 复用
- 凭据的加密存储与读取
- 登录态判定、失效识别、一次自动重登
- 承载上述能力所需的**最小登录界面**（输入框 + 登录按钮 + 错误提示），使 FR-01 可在真机上被用户验收

**不做（范围外，属其他 FR）**：

- **FR-02 统一身份认证（SSO）** —— 走 WebView，另行实现。本 spec 不得埋 SSO 的占位字段或空壳。
- **FR-24 生物识别** —— 另行实现。
- **FR-15 加载态/空态/错误态体系** 与 **FR-13 主题**、**FR-14 国际化** —— 横切能力，另行实现。本功能只做能用的最小错误提示，不引入主题与多语言框架。
- **FR-11 导航** —— 登录成功后先跳到一个临时占位页，不做标签导航。
- 注册、找回密码、修改密码 —— 网络学堂不提供，本项目也不做。

## 3. 设计（怎么做）

### 3.1 模块与文件

| 模块 | 文件 | 职责 |
|---|---|---|
| `model` | `auth.ets` | `Auth`、`LoginState`、`AuthError`（四分类）、`UserInfo`、`FailReason` 概念 |
| `model` | `urls.ets` | 网络学堂与统一身份认证的 URL 常量（对齐上游 `thu-learn-lib/src/urls.ts` 中认证相关项） |
| `common` | `logger.ets` | 分级日志，**内置凭据脱敏**：任何入参先经脱敏再输出 |
| `common` | `errors.ets` | 错误四分类的构造与归一（网络不可达 / 认证失败 / 接口语义变更 / 解析失败） |
| `network` | `sm2Format.ets` | SM2 密文裸格式：坐标补零、C1C3C2 拼接、公钥解析。**纯逻辑，不依赖系统能力** |
| `network` | `sm2.ets` | SM2 加密（调平台加密框架），产出服务端可接受的提交值 |
| `network` | `parse.ets` | 登录链路 HTML 抓取：SM2 公钥、漫游工单、CSRF 令牌、用户名的提取。**纯逻辑** |
| `network` | `cookieJar.ets` | 自管 Cookie：解析、按主机分组、注入。**纯逻辑**（见 §3.4） |
| `network` | `learnClient.ets` | HTTP 唯一出口：会话、CSRF 注入、失效自动重登、七步登录流程 |
| `storage` | `credentialStore.ets` | 凭据的唯一读写入口（关键资产存储服务） |
| `repository` | `authRepository.ets` | 编排：登录 / 登出 / 会话校验 / 用户信息 |
| `viewmodel` | `authStore.ets` | 应用级会话状态（单一 Store，见 ADR-0004），供页面订阅 |
| `pages` | `Login.ets` | 最小登录界面 |
| `pages` | `Index.ets` | 改为：未登录 → 显示登录界面；已登录 → 临时占位页 |

> **相对原设计新增 3 个文件**（`sm2Format.ets` / `parse.ets` / `cookieJar.ets`），理由一致：
> 把**与外部服务互操作的高风险逻辑**（密文拼接、页面抓取、Cookie 解析）做成不依赖系统能力的纯模块，
> 从而能在无设备环境下单元测试。这是实现期发现的重要约束——若与平台调用混在一起，
> 这些最易出错的逻辑将完全无法离线验证。

依赖方向严格遵循 `pages → viewmodel → repository → network/storage`，`model`/`common` 为叶子层（架构不变量 §1）。

### 3.2 登录流程（对齐上游 `thu-learn-lib@4.0.0` 的真实契约）

**这是本功能的核心，逐步照实复刻，不凭印象发挥**：

1. **清会话**：把 `id.tsinghua.edu.cn` 的 `JSESSIONID` 置空，确保总是从登录页开始（避免沿用他人/他次会话）。
2. **取 SM2 公钥**：`GET https://id.tsinghua.edu.cn/do/off/ui/auth/login/form/bb5df85216504820be7bba2b0ae1535b/0`，从响应 HTML 中提取 `#sm2publicKey` 元素文本，即公钥的十六进制串。
3. **提交登录**：`POST https://id.tsinghua.edu.cn/do/off/ui/auth/login/check`，表单字段：
   - `i_user` = 学号
   - `i_pass` = `'04'` + SM2 加密结果（详见 §3.3）
   - `singleLogin` = `on`
   - `fingerPrint` = 设备指纹（32 位十六进制，随机生成后持久化，见 §3.5）
   - `fingerGenPrint` = 空串、`fingerGenPrint3` = 空串（上游亦传空串；语义未知，**不臆测其含义**）
   - `i_captcha` = 空串
4. **取漫游工单**：从步骤 3 响应 HTML 中取首个 `<a>` 的 `href`，其 `ticket` 查询参数值即工单。
5. **漫游到网络学堂**：`GET https://learn.tsinghua.edu.cn/b/j_spring_security_thauth_roaming_entry?ticket=<ticket>`；非 2xx 即失败。
6. **取 CSRF 令牌**：`GET https://learn.tsinghua.edu.cn/f/wlxt/index/course/student/`，用正则 `/^.*&_csrf=(\S*)".*$/gm` 提取令牌；提取不到即判定为"接口语义变更"。该令牌**在登录/重登后失效**，必须随之刷新。
7. **后续请求**：对 `*.tsinghua.edu.cn` 的请求，一律以**查询参数** `_csrf=<token>` 追加（上游 `addCSRFTokenToUrl` 的行为）。

### 3.3 SM2 加密（本功能最大的技术风险点）

上游用 JS 库 `sm-crypto` 的 `sm2.doEncrypt(password, publicKey)`，其输出为**裸十六进制**，再前置 `'04'` 组成提交值。服务端期望的就是这个**非 ASN.1 的裸拼接格式**。

HarmonyOS 侧用 `@ohos.security.cryptoFramework`（非对称加解密当前仅支持 RSA 与 SM2，见官方 API 文档）：

- **公钥构造**：页面给的是裸十六进制（`04` + 32 字节 X + 32 字节 Y）。用 `createAsyKeyGeneratorBySpec()` 配合 ECC/SM2 密钥参数（由 X、Y 构造）得到公钥对象，**不走** PEM/X.509 路径。
- **加密**：SM2 非对称加解密，`init` 后直接 `doFinal`（该算法不支持 `update`）。
- **密文格式转换（关键）**：框架的密文为 ASN.1(DER)，而服务端要裸拼接。用 `SM2CryptoUtil.getCipherTextSpec(cipherText, 'C1C3C2')` 取出 `C1_X` / `C1_Y` / `C2` / `C3` 分量，再手工拼成 `'04' + C1_X + C1_Y + C3 + C2` 的十六进制串。官方文档明确提示：**拼接时 X、Y 分量若不足 32 字节须高位补零**。
- 该"手工拼接"是与外部服务互操作所必需的约束，代码处须留注释说明原因（否则后人会误以为是冗余代码）。

> 具体的公钥参数构造 API 形态需在实现期以官方文档与实机编译为准；若 `createAsyKeyGeneratorBySpec` 无法直接接受裸 X/Y，则改用 `ECCKeyUtil` 生成点参数，路线不变。此点列为 §6 待定项。

### 3.4 会话与 Cookie（实现期修正）

> **本节原设计已被实现推翻**：原计划用 `@ohos.net.http` 的 `enableAutoCookie(true)`
> 自动复用 Cookie，但实测该接口**起始版本为 API 26**，本项目 SDK 为 API 24，不可用。
> 改为**自管 Cookie 容器**（`network/cookieJar.ets`）。
>
> **该自管容器此后也已退役**（2026-09-27，随 ADR-0008 改为 WebView 主导登录）：
> Cookie 现由 `webview.WebCookieManager` 承载，见 **§8.1 第 6 条与 §8.5**。
> 本节以下描述属历史设计，保留以记录决策过程，**不再反映现状**。

- `LearnClient` 全程复用**同一个 `HttpRequest` 实例**。
- 每次响应后用 `response.cookies`（原始 Cookie 串，API 8+）更新自管容器；
  每次请求前按**主机名**注入 `Cookie` 请求头。
- **按主机名精确分组**，不做 Domain 匹配：本项目 Cookie 只落在
  `id.tsinghua.edu.cn` 与 `learn.tsinghua.edu.cn` 两个主机上，精确分组既够用又不引入歧义；
  登录横跨两个主机，分组错了会串会话。
- 重置会话即清空该容器（对齐上游"登录前清 JSESSIONID"的意图，且效果更强）。
- Cookie 串解析是纯逻辑，已单测覆盖（含属性剔除与跨主机隔离）。

### 3.5 凭据与设备指纹存储

存入**关键资产存储服务**（`@ohos.security.asset`），别名固定：

| 键 | 内容 | 说明 |
|---|---|---|
| `learnx.username` | 学号 | |
| `learnx.password` | 密码 | 仅在用户勾选"记住密码"时写入 |
| `learnx.fingerPrint` | 设备指纹 | 32 位十六进制随机串；**首次生成后持久化**，不随登录变化（上游每次登录用新随机值，本项目改为持久化以避免服务端把它当新设备；此差异记入 §6） |

- 唯一读写入口是 `storage/credentialStore.ets`；其余模块不得直接调用该 Kit。
- 登出（`CredentialStore.clearCredentials`）**清除学号与密码、保留设备指纹**。
  > **更正（2026-09-27，真机实测）**：原文写的是"登出时**必须**清除全部凭据与指纹"。
  > 那是错的，并且正是"每次登出再登录都要重新二次验证"的直接原因：指纹是**设备标识**，
  > 服务端靠它把本机认成同一台已登记的信任浏览器；登出把它清掉，下次登录就拿着全新指纹
  > 去登记，服务端认不出来（登记请求返回 `msg:"否"`，页面提示"未使用可信浏览器"）。
  > 上游 `learnX` 的 auth reducer 里**根本没有登出分支**，指纹永不清除。
  > 设备指纹不是凭据：不含用户信息、不由用户输入、服务端本就存有副本，本地也存于加密存储。
- 该选择与备选方案的取舍见 ADR-0007。

### 3.6 登录态判定与失效重登

- **失效信号**（对齐上游 `noLogin`）：响应最终 URL 含 `login_timeout`，或 HTTP 状态为 403。
- **自动重登**：带凭据的请求命中失效信号时，自动重登**一次**并重放该请求；再次失效则向上抛出认证失败，不再循环。
- 无凭据（用户未保存密码）时命中失效信号 → 直接抛认证失败，由页面引导重新登录。
- **错误四分类**（对应 ARCHITECTURE §5.4）：
  - 网络不可达（超时、DNS、连接失败）
  - 认证失败（凭据错误、会话失效且无法重登）
  - 接口语义变更（登录页找不到 SM2 公钥、找不到工单锚点、提取不到 CSRF、非预期状态码）
  - 解析失败（响应体结构不符预期）
- 服务端/网络问题**不得**报成应用缺陷。

### 3.7 重试

上游对登录本身有一次重试包装。本项目同样仅对**登录**加一次重试，且**只对网络不可达类**重试；认证失败与语义变更类**不重试**（重试无意义且会放大失败）。

> 第 8–11 项需在校园网内由用户确认。**单元测试全绿不替代它们**；在本项目具备校园网环境前，本 spec 不得标记为已交付。

## 7. 实现期重大发现：二次认证要求 WebView 主导登录（2026-09-27）

### 7.1 现象与证据

用真实账号登录时，登录校验返回的不是带工单的成功页，而是 **标题为「二次认证」的页面**（约 1661 字节）：

```
登录校验响应未含工单 len=1661 head= <!DOCTYPE html> ... <title>二次认证</title>
```

此时 Cookie 已正常携带（`cookieLen=52`），网络可达，编码格式（urlencoded / multipart）经对照实验证明服务端都接受。
**因此失败与网络、Cookie、编码无关，而是账号开启了二次认证。**

### 7.2 上游的解法（读 `robertying/learnX` 源码确证）

上游并非"API 直连"就能登录，它有一条 **WebView 主导的 SSO 流程**（`src/screens/SSO.tsx`
+ 注入脚本 `src/helpers/preval/sso.js`），其中**专门处理二次认证**：

1. 把**真实认证页**开在 WebView 里（`Cookie: ''` 起干净会话）；
2. 注入脚本 `setupLoginPage()` 把学号密码填进页面的 `input#i_user` / `input#i_pass` 并置只读；
3. **拦截 XHR**：当页面调用 `/b/doubleAuth/personal/saveFinger`（二次认证登记设备指纹）时
   **覆写请求体**，写入应用自己的 `fingerprint`、`deviceName`，并把 `radioVal` 设为 `'是'`
   —— 即自动回答"信任此设备"，使设备被登记，后续登录不再需要二次认证；
4. `overrideJQuerySubmit()` 在提交时注入 `fingerPrint`、勾选 `singleLogin`，并把**完整表单体**
   （含服务端页面生成的 `fingerGenPrint` / `fingerGenPrint3`）通过 postMessage 回传应用；
5. WebView 自己走完认证（含二次认证），导航到 `LEARN_ROAMING_URL` 时，应用取回抓到的表单数据，
   再执行 API 登录以建立会话。

**结论：`fingerPrint` / `fingerGenPrint` / `fingerGenPrint3` 是二次认证的设备信任标识，
只能由认证页的 JS 生成、经 WebView 抓取，API 直连无法获得。**

### 7.3 对本 spec 的影响（架构缺口）

- 原设计（本 spec §3 的纯 API 七步登录）**对开启二次认证的账号不成立**——不是缺陷，是范围缺口：
  PRD 中 FR-02（SSO）此前被列为 P2，而实际上**必须提升为登录主路径**，否则 P1 的 FR-01 对
  相当一部分账号（含本项目验收账号）根本不可用。
- 需新增/调整：
  - **新 ADR**：登录方式改为 WebView（ArkWeb）主导 + 设备信任登记；API 登录保留给无二次认证账号。
  - **PRD 调整**：FR-02 由 P2 提为 P1，并显式写明"处理二次认证与设备信任"。
  - **spec 调整**：§3 的登录流程需改写为"WebView 主导 + 从 WebView 抓取表单数据 + API 建会话"。
- Cookie 的取用方式也要随之调整：WebView 与 API 请求应共用 **`webview.WebCookieManager`**
  （进程级、同步读写、`saveCookieAsync` 可持久化），而不是各自维护容器。

> 该调整涉及架构决策与新 FR，按 SDD 流程需先经用户确认，**不得自行开工**。

### 7.4 更正：验证码由用户输入，注入脚本只处理"信任此浏览器"

§7.2 第 3 条曾把 XHR 拦截描述为"二次认证的解法"，**该表述不准确，此处更正**：

- **多因子认证的验证码（OTP）由用户在 WebView 中自行输入** —— 应用只预填学号与密码，
  其余步骤（输入验证码、确认信任该浏览器）都由用户在真实页面里完成。这正是"把 WebView 当浏览器用"的含义。
- 注入脚本拦截 `/b/doubleAuth/personal/saveFinger` 解决的只是页面弹出的
  **"是否信任此浏览器"询问**（写入应用设备指纹并把 `radioVal` 置为 `'是'`），**与验证码无关**。
- 上游的用户提示文案（`src/assets/translations/zh.ts`）确证了该交互设计：
  「请在即将打开的网页中完成登录。如需更改网页中预填的账号或密码，请关闭网页，再在 learnX 登录界面重新输入…」

**由此得出一个关键的运维约束**：设备信任走的是「**信任浏览器**」名单，且**有数量上限**。
故：
- 设备指纹必须**持久化复用**（每次登录换新指纹会迅速占满名额）；
- 用户可能撞上「信任浏览器数量已达到上限」，需引导其到
  `id.tsinghua.edu.cn` → 账号设置 → 多因子认证 → 信任浏览器数量 → 维护，删除旧设备。
  这条应作为可预见的错误提示写进实现（属 §3.6 错误四分类之外的可操作引导）。

> 结论不变（§7.3）：必须实现 WebView 主导的登录路径；变的只是对注入脚本作用的描述。

## 8. 修订后的登录流程（取代 §3.2，依据 ADR-0008）

> §3.2 的"纯 API 七步登录"保留为**备选路径**（仅适用未启用多因子认证的账号）。
> 主路径如下，实现以本节为准。

### 8.1 流程

1. **打开认证页**：应用内 `ArkWeb` 的 `Web` 组件加载
   `https://id.tsinghua.edu.cn/do/off/ui/auth/login/form/bb5df85216504820be7bba2b0ae1535b/0`，
   **以干净会话起步**（先清该域 Cookie）。
2. **注入预填脚本**（`Web` 的 `javaScriptAccess` + `onPageEnd` 后 `runJavaScript`）：
   - 填 `input#i_user` / `input#i_pass` 为学号与密码并置 `readOnly`；
   - 提交时给 `[name="fingerPrint"]` 写入应用持久化的设备指纹，并勾选 `singleLogin`；
   - **拦截 XHR**：当请求 URL 为 `/b/doubleAuth/personal/saveFinger` 时，覆写请求体，
     写入 `fingerprint`（应用指纹）与 `deviceName`，并把 `radioVal` 置为 `'是'`
     —— 即把"是否信任此浏览器"答为是，使设备进入信任名单；
   - 提交时抓取**完整表单体**（`FormData` → 对象），经 `Web` 的 JS 通道回传应用。
     **这三个值（`fingerPrint` / `fingerGenPrint` / `fingerGenPrint3`）只能这样获得。**
3. **由用户在该页面完成登录**，包括**输入多因子认证验证码**。
   **应用不得代填、不得代答验证码**——这是流程设计的一部分，不是遗漏。
4. **收尾判定**：监听导航请求；当目标命中网络学堂漫游地址
   （`https://learn.tsinghua.edu.cn/f/j_spring_security_thauth_roaming_entry`）时，
   视为认证完成，**停止页面导航并同时记下该 URL**——票据就在它里面（实测长度 36）。
5. **建立会话（两条路径，按可靠性排序，见 §10.2 与 ADR-0009）**：
   - **首选**：用上面记下的漫游地址直接发起漫游（`LearnClient.loginWithRoamUrl`），
     随后取首页 CSRF。不重新登录、不需要设备已被信任、**不清 Cookie**。
   - **兜底**：没截到票据或票据漫游失败时，改把抓到的表单体交给
     `LearnClient.loginWithFingerPrints`——取出 `fingerPrint` / `fingerGenPrint` /
     `fingerGenPrint3` 三项设备信任标识，在**全新会话**里重新登录（密码由新会话的公钥重新加密）。
   两条路径完成后都取得 CSRF 令牌，后续 API 请求照旧。
   > **更正（2026-09-27，真机实测）**：本节初稿写的是"凭据不再自行加密，改为直接使用页面生成的
   > 表单体"（即原样重放那份密文）。**那是误读**：ADR-0008 说的是"以抓到的表单数据执行既有
   > API 登录流程"，其真实含义与上游一致——抓表单体的目的只是拿到三个应用构造不出的设备信任
   > 标识。原样重放行不通（`i_pass` 与页面那次会话绑定），真实账号下表现为拿不到漫游工单、
   > 被误报成"学号或密码错误"。详见 §8.6。
6. **Cookie 统一**：WebView 与 API 请求共用 `webview.WebCookieManager`
   （`configCookieSync` 存入 / `fetchCookieSync` 取出 / `saveCookieAsync` 持久化），
   替代自写内存容器；`storage/CredentialStore` 仍只负责学号密码与设备指纹。

   → 密码恢复为 `@State`（它是按钮可用性的输入之一），`text` 绑定仍不写。
2. **进入 SSO 页即失败**：`startSso` 先把状态切到 SSO 页、**再**准备注入取值，
   SSO 页在取值就绪前渲染，直接落进"缺少取值"分支（日志：
   `已清空全部 Cookie` 紧跟 `缺少网页登录所需的取值，无法注入`）。
   → 取值备齐后再切状态。

> 这两处都不是静态检查或单测能发现的。本项目至今 6 个缺陷全部是实机跑出来的。

#### 仍需用户完成（T15）

- 真实账号 + 校园网，在模拟器/真机上完成一次登录：**多因子认证的验证码必须由人输入**。
- 之后需确认：重新登录成功（工单 → 漫游 → CSRF）、进入应用后杀进程重开仍是登录态
  （即 `WebCookieManager` 的会话被读回，日志应出现 `沿用已持久化的会话`）。

## 9. 真实账号首次运行的发现与纠正（2026-09-27，用户执行）

### 9.1 现象

用户用真实账号（已启用多因子认证）完成了一次登录：

1. 能进入登录页、能输入验证码；
2. 输入验证码后页面弹出：
   **「您的浏览器目前处于隐私或匿名模式，系统无法将该浏览器设置为信任浏览器。如需启用这一功能，请退出隐私或匿名模式。」**
   （消息键 `double_sfjbsbbjwxrsb3`）与 **「您本次登录未使用可信浏览器，将无法支持统一登录。」**（`yinshiyongyinsi`）
3. 点「确定」后页面显示**登录成功**；
4. 随后应用退回登录界面，报「学号或密码不正确，或登录已失效」（归类为**认证失败**）。

### 9.2 两条根因（一条是我的读错，一条是平台默认值）

**① 「重新登录」被误实现成「重放页面表单体」。**
本 spec §8.1 第 5 条与 `LearnClient.loginWithFormData` 初版把 ADR-0008 的
「以抓到的表单数据执行既有 API 登录流程」读成了"原样重放那份密文"。
但 `i_pass` 是页面用**它那次会话**的 SM2 公钥加密的，密文与会话绑定；重放要求我们的请求
恰好带着页面那次会话，实测拿不到漫游工单——服务端返回的响应既无工单也不含「二次认证」字样，
于是落进"未取得漫游工单，通常是学号或密码错误"，把**会话问题误报成了密码问题**。
逐行读上游后确认其做法：抓表单体的目的只是拿到 `fingerPrint` / `fingerGenPrint` /
`fingerGenPrint3` 三个应用构造不出的设备信任标识，随后**新开会话、重新加密密码再登录**
（`thu-learn-lib` 的 `login(username, password, fingerPrint, fingerGenPrint, fingerGenPrint3)`）。
→ 已改为 `LearnClient.loginWithFingerPrints(credentials, prints)`，两条路径共用
`performLogin`，差别只在是否带上这三项；`SsoFormBody.endpoint()` 随之删除。

**② 页面判定"隐私/匿名模式"，因而拒绝登记信任浏览器。**
从校方页面取下的 JS 显示它用 `localforage`（IndexedDB → WebSQL → localStorage）持久化设备标记
（`/v2/dist/doubleauth/localstorageUtil.js`，由 `/ui/auth/js/finger3.js` 把结果写入 `#fingerGenPrint3`）。
而 ArkWeb 的 `domStorageAccess` 与 `databaseAccess` **默认都是关闭**——初版只开了前者。
→ 已补 `.databaseAccess(true)`。

> **但环境探测（§9.3）在模拟器上给出的是**：
> `cookieEnabled=true cookieLen=0 localStorage=ok sessionStorage=ok indexedDB=present`。
> 也就是说 **localStorage 的写入-读回是通的、IndexedDB 也在**——"存储不可用"这个推断
> **不成立**。
>
> **这条推断后来被真实账号运行直接证否**（见 §11.2）：「保存信任浏览器」请求服务端返回的
> 是 **`status=200 result=success`**——登记**成功了**。那句"隐私或匿名模式"是页面自己弹的
> **客户端提示**，它并没有阻止登记。
> （`cookieLen=0` 不构成异常：会话 Cookie 是 HttpOnly，本就看不到 `document.cookie`。）

> 附带的现实影响：即使登录走通，**只要信任浏览器登记失败，每次登录都会再要一次验证码**。
> 这不是缺陷（是校方的设备信任机制），但要按 §8.2 的引导让用户知道怎么处理。

### 9.3 为此补上的诊断（下一次真实账号运行即可定论）

诊断只报**可用性与长度**，不含任何值：

- 注入脚本回报页面环境：`cookieEnabled` / `document.cookie` 长度 / localStorage **写入-读回**结果 /
  sessionStorage / IndexedDB 是否存在（只探存在性，不给校方域建库）。
- 回报「保存信任浏览器」请求的实况：**是否发出过**、请求体是否被改写、服务端的
  `result` 与状态码——这是"信任浏览器到底存上了没有"的唯一答案。
- 提交时回报三项设备信任标识的**长度**（长度为 0 即页面没拿到）。
- 应用侧在取登录页与提交时记录 `cookieLen`（HTTP 客户端与 WebView 是否真的共用同一份会话），
  并在缺失工单时记录响应的**归类**（登录页 / 二次认证页 / 未识别页面）。

- §9.2 ① 的纠正已实现并通过静态门（`check arkts` 主源码 21 文件 + 测试 7 文件 0 错、`check lint` 0 问题、

## 10. 真实账号第二次运行：把"信任浏览器"这一步的影响绕开（2026-09-27）

### 10.1 现象与它的价值

用户第二次用真实账号运行：**页面依旧提示"浏览器处于隐私或匿名模式、未使用可信浏览器"**，
但应用侧的报错从上次的「学号或密码不正确」变成了
**「网络学堂接口似乎有变化，暂时无法登录」（归类 接口语义变更）**。

**这个变化本身是有效证据**：上次是"响应无工单且不像二次认证页"，这次是"响应就是二次认证页"。
也就是说 §9.2 ① 的纠正生效了——服务端确实返回了二次认证页，被正确归类，不再被误报成密码错误。
剩下的真相只有一个：**设备没被登记为信任浏览器，于是服务端的任何 API 登录都会再要验证码**。

### 10.2 由此确定的设计：票据优先，绕开重新认证

既然"没登记信任浏览器 ⇒ 重新登录必被要验证码"，那么**任何形式的重新登录都不可依赖**。
能绕开整个重新认证的只有一条路：**用浏览器自己正要用的那张漫游票据**。

- 认证完成后，页面会导航到 `…/f/j_spring_security_thauth_roaming_entry?ticket=<票据>`；
  我们在 `onLoadIntercept` 取消这次导航时，**票据就在那个 URL 里**。
- 首选路径：拿这个 URL 直接发起漫游（`LearnClient.loginWithRoamUrl`），随后取首页 CSRF。
  它不需要密码、不需要设备已被信任，且**不清 Cookie**——浏览器自己发这一步时也带着会话。
- 兜底路径：没截到票据、或票据漫游失败时，才回退到"带设备信任标识重新登录"（§9.2 ①）。
- 两条路都记日志（`建会话方式=漫游票据|重新登录`），下一次运行即可知道走的哪条。

> **对 ADR-0008 的偏离要说明白**：ADR §决策 4 写的是"停止页面导航并取用第 2 步抓到的表单数据"，
> 本实现改为"停止导航，取用**同一处**截到的漫游地址里的票据"（表单数据仍用于兜底路径）。
> 架构没有变（取消导航 + 由 API 侧建会话），变的是"用什么建会话"。
> **该偏离已确认并固化**（2026-09-27）：用户确认"票据优先"，决策写入
> [ADR-0009](../adr/0009-login-finish-via-roaming-ticket.md)（**已接受**）。按 ADR 不可变约定，
> ADR-0008 正文不改写，仅标注其"建会话方式"部分已被 0009 取代。

### 10.3 诊断补强（只加事实，不加值）

- 「保存信任浏览器」请求的**结果改为即时回报**（此前只在提交时汇总，会漏掉它）——
  这是"信任浏览器到底登记上没上"的唯一答案，也是本次唯一还缺的关键事实。
  **回报内容含三项**：请求体是否被我们改写（`改写=是/否`）、服务端 RPC 的 `result`、
  以及**响应体的脱敏摘要**（长值折叠为 `<长值>`，保留字段名与短值/中文提示）。
  加后两项的原因：首轮只记 `result`，而 `result` 只是 RPC 信封——
  页面那句"无法设置为信任浏览器"的真实原因只可能在响应体里。
- 环境探测补上 **User-Agent**（实测：`Mozilla/5.0 (Phone; OpenHarmony 6.1) … Chrome/132.0.0.0 Safari/537.36  ArkWeb/6.1.0`）。
  页面那句"隐私或匿名模式"的判定依据仍未知，UA 是候选之一，先记下来。
- 收尾时回报**漫游地址的参数名与票据长度**（不记票据值），以便确认首选路径是否真的可用。

### 10.4 状态

- 静态门全绿（`check arkts` 21 + 7 文件 0 错、`check lint` 0 问题、`hvigorw test` **65/65**），
  注入脚本语法检查通过，已重新构建安装到模拟器并冒烟通过（假凭据下页面加载、预填、探测均正常）。
- **首选路径能否成功仍未经真实账号验证**；下一次运行的日志会给出
  `收尾：漫游地址 参数=[…] ticket长度=…` 与 `建会话方式=…` 两行结论。
- 因此本 spec 仍**不得**标记为已交付。

### 11.7 「登出后再登录仍需二次验证」：已定位并修复

用户复测：**登出再登录仍需二次验证，通过后页面依旧提示"隐私浏览器"**。逐项查清如下。

**告一段落的事实**：探测补上响应体后，登记请求的真实答复是：

```
信任浏览器请求 改写=是 status=200 result=success
响应={ "result" : "success", "msg" : "否", "object" : null }
```

`改写=是` 说明我们的改写**生效了**（`radioVal=是` 确实发出）；但服务端明确回 **`msg:"否"`**
——**它拒绝把本机登记为信任浏览器**。页面那句"隐私模式"是它对这次拒绝给出的解释。

**找到的直接原因**：登出后日志紧跟一句 `已生成新的设备指纹`——**我们的登出把设备指纹也清掉了**
（`CredentialStore.clear` 原先连指纹一起删）。指纹是服务端认设备用的标识，清掉它意味着
**每次登出再登录都拿着一个陌生指纹去登记**，服务端当然认不出来。
这与 ADR-0008 自己写的"设备指纹必须持久化复用"直接矛盾，上游则是永不清除
（其 auth reducer 没有登出分支）。

**已修的**：

1. `CredentialStore.clearCredentials()` 取代原 `clear()`：登出只清学号与密码，**保留设备指纹**。
2. 指纹复用也留痕（`复用已有设备指纹` / `已生成新的设备指纹`），下次运行一眼可辨。
3. 清 Cookie 由"清空全部"改为"**只清会话 Cookie**"（`clearSessionCookieSync`）：
   原先 `clearAllCookiesSync` 连持久 Cookie 一起抹掉，而上游只清 `id` 域的 `JSESSIONID`——
   若服务端用持久 Cookie 认设备，我们每次都把它擦了。官方文档也提示
   "如需仅清除会话 cookies，请使用 `clearSessionCookieSync`"。
4. 新增两条排障事实：`进入登录页前/清除后 id 域 Cookie=[名字…]`（只记名字），
   以及登记请求体的**字段名与各值长度** `登记请求体 [fingerprint:32 …]`
   —— 后者用于回答"页面自己有没有拿到 `fingerGenPrint3`"，这是服务端回 `否` 时唯一未排除的变量。

**诚实说明**：第 1 条有直接证据（日志里的指纹轮换）且与上游一致；
但**首次登录**（此前从未登出）也曾得到 `msg:"否"`，所以指纹轮换不是唯一原因。
下一次运行的 `登记请求体 [...]` 会显示页面侧字段是否齐备，据此再判。
在此之前不得宣称这个问题已解决。

### 11.8 「这次直接登不上」：注入脚本的误报把**已经成功的认证**掐断了（已修）

用户下一次尝试直接失败，应用提示「网络学堂接口似乎有变化」。日志只有两行：

```
[ssoLogin] 登录页上报异常 type=PREFILL_FAILED
[authStore] 网页登录异常 code=PREFILL_FAILED reason=API_CHANGED
```

而用户同期的截图显示页面**已经走到门户**（清华 logo + 菜单 + 「二次验证成功」与信任浏览器提示）
——也就是说**认证其实在正常推进**。对照后确认根因：

- 注入脚本用 `javaScriptOnDocumentStart` 注入，**会在每一个文档上执行**；
- 它在"找不到登录表单"后等 20 秒就上报 `PREFILL_FAILED`；
- 验证码通过后页面跳到门户（登录页脚本已不复存在），此时它把**门户文档**误判成
  "登录页结构已变"，上报失败 → 应用按"接口语义变更"中止流程，把用户踢回登录界面。

> 同一份脚本在第一次成功登录时没触发，只是**运气**：那次流程在 20 秒窗口内就走完了，
> Web 已经被销毁，误报无处投递。

**修法**：把判据从"页面上找不到表单"收紧为"**当前文档按 URL 就是登录表单页**
（`/do/off/ui/auth/login/form/`）却仍然填不进去"——只有这一种情况才算真的页面结构变更。
非登录表单页到期时**保持沉默**，并记一条诊断（`预填检查：当前文档不是登录表单页，保持沉默 pathname=…`），
使"它确实没误报"在日志里可见。顺带两处加固：

1. 到期后**主动复查一次**（原先只靠 DOM 变动触发，页面静止时判断永远不会发生）。
2. 「信任浏览器数量」提示的识别串收紧为「信任浏览器数量**已达到上限**」——
   门户页侧边若出现同名菜单项，原先也会误命中并中止流程。

实测（模拟器、假凭据）：登录表单正常预填，**26 秒后无任何误报**；
设备指纹日志为 `复用已有设备指纹`（§11.7 的修复生效）。

### 11.9 「浏览器处于隐私或匿名模式」的确切来源：校方页面的误报（已绕开）

用户复测仍见该提示，并追问"是不是测试环境强制要求浏览器处于隐私模式"。这次把判定读到了源码级。

**先证伪了"环境强制"**：应用侧直接问 ArkWeb —— 日志 `Web 隐私模式=false`。
即**我们的 WebView 根本不是隐私模式**，那句提示是校方页面**自己算出来的**。

**再定位到算法**：从"二次认证页"的脚本清单拿到它唯一的业务 bundle
(`/v2/dist/doubleauth/doubleAuth.bundle.js`)，其中 `isPrivate` 来自第三方库
**`detectIncognito` v1.4.1**（github.com/Joe12387/detectIncognito）。它的 Chrome 分支判据是：

```js
navigator.webkitTemporaryStorage.queryUsageAndQuota(function (usage, quota) {
  n(Math.round(quota/1048576) < 2 * Math.round(heapSizeLimit/1048576));   // 配额偏小 ⇒ 隐私模式
}, …)
```

**实测数据**（注入脚本复刻同一条公式，报出它会得出的结论）：

```
隐私判定输入 分支判据=51 estimate=有 webkitTemporaryStorage=有 jsHeapSizeLimit=2190000000
隐私判定结论(修复前) isPrivate=true  配额MB=3504  阈值MB=4178
```

ArkWeb 报的临时存储配额 **3504 MB** 低于阈值 **4178 MB**（=2×2.19GB 堆上限）→ 库判定隐私模式。
这是**移动端 WebView 上的典型误报**：它把"配额读数偏小"当成了隐私模式，与真实隐私模式无关。

**误报的实际后果**：页面据此在对话框里**只提供"否"**（不信任此浏览器）→ 设备信任登记永远登记不上
（服务端回 `msg:"否"`）→ **每次登录都要重新二次验证**。

**处置**：在 `sso_inject.js`（文档开始即注入，先于页面脚本）把两个"配额查询"接口的读数抬到阈值之上
（`navigator.storage.estimate` 与 `navigator.webkitTemporaryStorage.queryUsageAndQuota`，
就地替换方法、不动对象本身）。它是客户端启发式而非安全控制；是否信任此浏览器由页面询问用户，
而那个回答本就按用户意图由本脚本置为"是"。修复后实测：

```
隐私判定结论(修复后) isPrivate=false 配额MB=65536 阈值MB=4178
```

> **一处几乎铸成的误报（留作教训）**：第一版把配额设成 4 GB，看似生效（页面上那句文案不再出现），
> 但按公式一算 **3815 MB 仍 < 4178 MB**，判据并未翻过阈值；"文案没出现"只是因为**该对话框在
> 那一页尚未渲染**。为此补了 `隐私判定结论(修复前/后)` 这条**直接复刻其公式**的诊断——
> 它才是在任一页面上都能自证的判据。教训：**"现象消失"不等于"原因被修好"**。

**仍待用户确认**（需验证码）：完成一次完整登录后，① 二次认证页上那句隐私提示应消失且对话框
出现"是/否"选择；② 设备信任登记应被接受（`登记请求体 [...]` 与 `响应={…}` 两行会显示）；
③ 之后再登录一次应**不再要求验证码**。

### 11.10 「网络异常，请重新登录或稍后重试」：注入脚本自己抛异常把请求掐了（已修）

§11.9 的修复见效了——用户复测时页面已给出正确的询问：
**「是否将本次登录使用的设备及浏览器记为信任浏览器？」**，且"是"已预选（隐私误报消失）。
但点「确定」后页面显示 **「网络异常，请重新登录或稍后重试」**，两遍都不行，**且应用侧一条相关日志都没有**。

**根因是我自己引入的缺陷**：早先清理死代码时删掉了 `var sawSaveFinger` 的声明，
却把 `sawSaveFinger = true;` 这句赋值留在了拦截分支里。脚本以 `'use strict'` 运行，
**给未声明的标识符赋值会抛 `ReferenceError`**；而这句就在 `XMLHttpRequest.prototype.send`
的覆盖函数第二行，于是：

1. 页面调用 `saveFinger`（`$.ajax`，`timeout: 5000`）→ 我们的覆盖函数一进去就抛异常；
2. **请求根本没发出去** → jQuery 的 fail 分支 → 页面显示那句"网络异常"；
3. 异常发生在任何打点**之前** → 应用侧没有任何日志，排障方向被完全带偏。

**修法**：删掉那句赋值。并补两道之前缺掉的能力：

1. **不依赖 JS 桥的观测通道**：应用侧新增 `.onConsole()` 转发，脚本内新增 `mark()`
   （同时写页面控制台与 JS 桥）——桥在子框架里未必可用（cef 日志出现过
   `native proxy object not found, name:learnXSsoBridge`），而这次的关键信息全在页面侧。
2. **`scripts/check-sso-inject.mjs`：注入脚本的入口点检查**。`node --check` 只查语法；
   把脚本丢进桩沙箱"执行一遍"也不够——出问题的代码在事件回调里，不调用就永不触发。
   该脚本在桩沙箱里执行脚本、**推进它注册的定时器**，并**主动调用被覆盖的 `send`**
   （普通 URL 与 `saveFinger` 两条路径），断言请求体被改写为 `radioVal=是`。
   **已验证它能抓住本次这个 bug**（临时把坏行加回去，它准确报出
   `ReferenceError —— sawSaveFinger is not defined` 以及"改写未生效"）。
   该检查已并入提交前门（见 `.claude/rules/static-analysis.md` §2）。

> 另有一条待观察：登录页存在一个未处理的 Promise 拒绝（`未处理的拒绝 [object Object]`，
> 原因对象无 `message`，暂未能命名）。页面用 localforage 取设备标记，它失败会让
> `#fingerGenPrint3` 一直为空（实测提交时长度为 0）。**这与票据路径无关**，但若后续
> 需要让"重新登录"兜底路径也可用，就得查清它。
