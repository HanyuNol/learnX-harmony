# 功能规格：作业截止提醒（写入系统日历 + 提前提醒）

> 状态：开发中　·　关联 PRD：FR-18（与 FR-16 / FR-19 的边界见 §2）　·　分支：main
> 交互参照上游 `robertying/learnX` 的 `helpers/event.ts`（`saveAssignmentsToReminderOrCalendar` /
> `saveAssignmentEvent`）、`data/reducers/settings.ts`（`alarms` 默认值）、
> `screens/CalendarEvent.tsx`。**只取语义，不移植代码**（ADR-0001）。
> 平台能力用 **Calendar Kit**（`@ohos.calendarManager`）。

## 0. 载体变更（2026-09-28，用户决策）

本 FR 起初按**后台代理提醒**（`@ohos.reminderAgentManager`）实现并过了全部门与部分设备验收，
随后按官方文档查明：**手机、平板、PC/2in1 对代理提醒存在管控，普通应用默认不可用**
（错误码 `1700002` 的官方"可能原因"第一条即"没有使用权限时该应用提醒数量上限视为 0"；
实测任何参数、任何类型的登记都报此码，有效提醒恒为 0，而权限已授予、通知已开、
设备有 `ReminderAgentService`）。官方给出两条出路：**改用 Calendar Kit** 或向华为申请代理提醒
权限。**用户 2026-09-28 决定改走 Calendar Kit**（普通应用的日历读写是 `user_grant` 级权限，
能立刻在真机/模拟器上生效；上游在 Android 上正是"日历事件 + 闹钟"这一套），故：
代理提醒那套实现（`native/reminderAdapter`、`PUBLISH_AGENT_REMINDER` 权限）**已删除**，
不留两套载体（用户未选"两者并存"）。

代价（如实记录）：提醒由**系统日历**弹出（而不是本应用自己的通知），
且需要用户授予日历权限；好处是今天就能真正生效，并且这套管道**就是 FR-19 要用的那一套**。

## 1. 背景与目标

作业有截止时间，但用户不一定会主动打开应用去看——**错过截止**是这个应用最实际的损失。
本 FR 让"作业截止"进入用户的**系统日历**：在截止时刻前提醒（默认提前 24 小时），
由系统在到点时刻弹出通知，不依赖应用进程存活。

## 2. 需求（要什么）

**范围内**：

1. 设置页「提醒」一组，三项（沿用已实现的那三个，语义对齐上游）：
   - **作业截止提醒**（开关，默认关）。关闭时不登记任何日程，并清掉此前登记的。
   - **提前多久提醒**（整数分钟，默认 **1440** = 24 小时，对齐上游
     `assignmentReminderAlarmOffset ?? 24 * 60`）。允许 `0`（= 在截止时刻提醒）。
   - **已完成不提醒**（开关，默认关，对齐上游 `assignmentCalendarNoAlarmIfComplete`）。
2. 登记规则（对齐上游 `saveAssignmentsToReminderOrCalendar` 的筛选）：
   - 只登记**未过期**的作业（上游 `dayjs(deadline).isAfter(dayjs())`，严格晚于当前时刻）；
   - 每个作业一条日程：**标题** `作业名 - 课程名`；**描述** 截止时刻（`YYYY-MM-DD HH:mm`）
     与正文摘要；**结束时间** = 截止时刻、**开始时间** = 截止时刻 − 30 分钟
     （对齐上游 `calendarEventLength ?? 30` 的"截止前半小时"这块）；
   - **提醒** = 距开始时间提前 `提前量 − 30` 分钟（负值表示开始之后，即正好落在截止时刻）；
     若该提醒时刻**已经过去**（现在离截止已不足一个提前量）则**不设提醒**——
     系统对"已过提醒时间但未结束"的日程会**立即提醒**，那等于当场弹一条无意义的通知；
   - 作业本身**仍会写进日历**（只是没有提醒），因为"日历里能看到截止"本身有价值。
3. 同步时机：作业数据**落地后**自动对齐（加载成功 / 改动设置），不要求用户手动点同步
   （上游要手动点一次，忘记点就等于没有提醒）。
4. 点日历里的日程可看到标题/描述与截止时刻；用户可在日历应用里隐藏/删除本账户。
5. **权限与失败如实**：未授予日历权限、或系统拒绝写日程时，**不影响主流程**，
   并在设置页「提醒」组下**常驻**提示（不是一闪而过的 Toast）。

**不做（范围外）**：

- **课程事件 / 课表同步**（含上游 `saveCoursesToCalendar`、`courseAlarm`、地点省略）：属 FR-19；
  本 FR 只做作业截止（共用同一套日历管道，FR-19 到时复用）；
- **第二提醒**（上游 `assignmentCalendarSecondAlarm` + 30 分钟那一条）：不做——一条足够，
  两条只会让"提前多久"的设置语义变含混；
- **事件时长设置项**（上游 `calendarEventLength`）：固定 30 分钟，不新增设置行；
- **一键服务日程 / DeepLink 回跳**（Calendar Kit 的 `service`）：不做，需求里没有；
- **重复日程**：作业是单次截止，不用 `recurrenceRule`；
- **写入系统默认日历**：写进**本应用自己的日历账户**（上游同样自建日历），
  理由是可整账户隔离、整批清理、用户能单独隐藏；
- **后台定时轮询新作业**：属 FR-25。本 FR 只在"应用内拿到作业数据"时对齐一次；
- **应用内定时器 + 自建通知**：不做——应用不常驻后台，这种提醒在应用被杀后不会响，
  属于"看起来有、其实没有"的实现。

## 3. 设计（怎么做）

### 3.1 上游事实（对照基线，逐行核过）

| 事实 | 出处 |
|---|---|
| 只同步**未过期**作业：`[...assignments].filter(item => dayjs(item.deadline).isAfter(dayjs()))` | `helpers/event.ts:325-327` |
| 标题 `assignment.title + ' - ' + course.name`；备注 `removeTags(assignment.description)`；完成的前缀 `✅ ` | `helpers/event.ts:205,336-345` |
| 日程时长 = `settings.calendarEventLength ?? 30` 分钟，**结束时间就是截止时刻** | `helpers/event.ts:210-211` |
| 提醒 = 相对**开始时间**偏移 `-(assignmentCalendarAlarmOffset ?? 24*60)` 分钟 | `helpers/event.ts:207-218` |
| "完成则不提醒"：`assignmentCalendarNoAlarmIfComplete && completed` → 不给闹钟（日程仍在） | `helpers/event.ts:203-206` |
| 自建日历账户（`learnX 课表` / `learnX 作业`），已存在则复用、找不到就建 | `helpers/event.ts:64-158` |
| 去重用 `syncedReminderAssignments: {[assignmentId]: eventId}`；存在则 `update`，否则 `create` | `helpers/event.ts:170-200` |
| `alarms` 全部默认 `false`，偏移无默认值（取值处 `?? 24*60`） | `data/reducers/settings.ts:30-36` |

> 两处**有意偏离上游**：① 上游关闭开关不清已登记项（留幽灵日程，靠单独的"删除已同步"入口清理），
> 本项目**关闭即清**；② 上游手动触发同步，本项目**数据落地即对齐**。

| 结论 | 出处 |

| 日历/日程的读写是**用户授权**级普通权限：`ohos.permission.READ_CALENDAR` / `WRITE_CALENDAR`（`user_grant`/`normal`） | `权限定义` 与《Calendar Kit 简介》约束限制 |

另有两条**实测约束**（2026-09-28，模拟器 learnx / HarmonyOS 6.1.1(24)，都是踩出来的）：

| 实测 | 处置 |
|---|---|
| 用 **ApplicationContext** 调 `calendarManager.getCalendar()` 一律报 `201`（权限拒绝），而权限查下来是已授予的（`reqPermissionStates [0,0,0]`） | 日历接口**必须传 UIAbilityContext**（官方样例也都用 Ability 上下文）；`pages` 传 `getUIContext().getHostContext()`，见 `viewmodel/reminderSync` 的类型与说明 |

### 3.4 关键规则

1. **纯逻辑与系统调用分离**（`testing-and-quality.md` §1.1）：筛选、时刻计算、标题描述、
   文本解析、差量对齐全在 `model/reminder.ets`，宿主侧可穷举；`native/calendarAdapter` 只做
   "把参数交给系统、把系统结果带回来"。
2. **身份写在 `identifier` 上，不落本地映射表**：`identifier = learnx:<课程 id>:<作业 id>`
   （API 12+ 的"写入方指定唯一标识"，查询默认返回）。对齐时"读该账户现有日程 → 比期望 →
   多则删、少则加、变则删了重建"，无本地状态、可自愈——上游用 `syncedReminderAssignments`
   映射表，表一丢/错就永远对不上。
3. **写进系统默认日历账户，不自建账户**：原设计与上游一致（自建 `learnX 作业` 账户），
   但 2026-09-28 实测 `createCalendar()` 报 `201`（权限拒绝，而读写权限都已授予），
   官方文档给的替代路径正是默认账户（"若不关注 Calendar 归属，直接使用默认 Calendar"），
   且权限对照表明确允许"增删改**默认账户下当前应用创建的**日程"。身份改由 `identifier` 认领
   （见第 2 条），正确性不依赖账户归属。**代价**：这些截止日程与用户自己的日程同处一个日历，
   不能整账户隐藏/删除——如实记在 §6。
4. **"该不该动"看三件事**：不在期望集合里的（已截止 / 已提交且勾了"已完成不提醒" /
   已不在当前学期）要删；在集合里但**开始时间或提醒时刻变了**（老师改了截止时间）要删了重加；
   其余原样留着，避免每次刷新都重写用户的日历。**没有 `identifier` 的日程一律不动**
   （用户自己加进该账户的，或本应用早期版本的）——不认识的东西不删。
5. **关闭开关即清**：关闭时不登记任何日程，并删掉本账户下**本应用写的**全部日程。
6. **过去时刻不设提醒**：提醒时刻已过去的作业仍写进日历，但 `reminderTime` 不填
   （系统对已过的提醒时间会**立即弹**，那是噪音不是提醒）。
7. **作业数据不完整时一条也不动**（上一批修复的缺陷，继续有效）：对齐是"以期望集合为准、
   多则删"，而**空集合等于"一条都不要"**。作业尚未加载、或部分课程请求失败时若照算，
   会把用户日历里已有的日程成批删掉而用户毫不知情。故调用方必须传 `dataComplete`
   （= 当前学期每门课都取到了），为假时不做任何变更；关闭开关是唯一例外。
8. **权限被拒不影响主流程**：读不到/写不了日历时只记日志 + 设置页常驻提示，
   作业列表、设置页其它操作照常（`ARCHITECTURE.md` §5.5 "尽力而为"，
   `testing-and-quality.md` §2 第 7 条）。
9. **不做条数上限**：上一版按代理提醒的"API ≤25 上限 30 条"做了截断；日历日程没有这个限制
   （官方未给每账户/每应用日程数上限），**人为截断用户日历里的截止日程只会造成"某些作业不提醒"
   的隐形缺口**，故取消截断（原 `MAX_REMINDERS` 与其单测一并删除）。
10. **日程时间用 13 位时间戳**（官方要求），UTC 毫秒即 `Date.now()` 同一量纲。

## 5. 验收标准

**自动化可验证（单元测试，不依赖设备）**：

1. 筛选与时刻：只收未过期作业；`deadlineTime <= 0` 不收；勾了"已完成不提醒"时跳过已提交的；
   开始/结束时间 = 截止 −30min / 截止；`reminderMinutes = 提前量 − 30`；
   提醒时刻已过去时 `reminderMinutes` 为 `null`（日程仍生成）。
2. 标题与描述：标题 `作业名 - 课程名`；描述含 `YYYY-MM-DD HH:mm` 形式的截止时刻与摘要，
   **不含界面文案**（`native` 侧取不到 `Resource`，故只放语言无关的数据）。
3. 提前量文本解析：`0` 与正整数通过；空串 / 非整数 / 负数 / 带小数 / 超上限（14 天）→ 拒绝。
4. 差量对齐：新增则加；不在期望里的则删；**开始时间或提醒时刻变了**则删了重加；
   完全相同 → 空计划（幂等）；没有 `identifier` 的**不动**；同一标识出现两次 → 删掉后来者。
5. 静态门：`check arkts`（主 + 测试显式传路径）、`check lint` 零错误；`build` 成功；
   `check-l10n` 键集合一致。

    （`aa start` 报"暂无可用打开方式"），故无法排除"提醒依赖日历应用"。
    → **需真机确认**（这也正是本 FR 唯一剩下的验收项）。
11. ✅ 勾"已完成不提醒"后：`期望` 从 6 降到 2、`删除=4`（4 条已提交的作业被撤下），
    未提交的 2 条**仍在日历里**；取消勾选后 `新增=4` 恢复。

**需用户确认**：第 10 项在**真机**上确认一次；以及"提醒出现在系统日历里"这一产品形态是否符合预期
（这是本次载体变更的代价，见 §0 与 §6）。

## 6. 风险 / 待定

| 项 | 说明 | 处置 |
|---|---|---|
| 用户不授予日历权限 | 权限被拒是常态而非异常 | 主流程不受影响；设置页常驻提示；开关位置保留用户意图（不硬弹回） |
| 提醒来自**系统日历**而不是本应用 | 载体变更的直接代价（见 §0） | 已在 §5 列为需用户确认项；若用户更看重"本应用自己的通知"，唯一出路是申请代理提醒权益（当时的选项 A） |
| 日程与用户自己的日程同处默认日历 | 载体变更 + 平台约束（自建账户 `createCalendar` 被拒，见 §3.4 第 3 条） | 身份靠 `identifier` 认领，不认的一律不动；用户不能整账户隐藏。若将来平台允许自建账户，可改回（属实现替换，不影响纯逻辑） |
| 用户删掉某条日程 | 单条被删 | 下次对齐补回（幂等对齐天然覆盖）；用户若反复删除会被反复补回——目前无"忽略"机制，观察后再说 |
| 学期间切换会清掉旧学期的日程 | 对齐只按"当前学期的作业数据"算 | 有意如此（应用此刻展示的就是 B 学期）；设置页说明"对齐的是当前学期的作业"。若用户希望保留，改法是把已登记项并入期望集合——待用户表态 |
| 提醒时刻**晚于**截止 | 提前量为 0 时提醒落在截止时刻（`reminderMinutes = -30`，负值＝开始之后） | 允许（上游同样允许）；只在截止仍在未来时登记 |
| 日程数量 | 官方未给每账户日程数上限；已取消人为截断（§3.4 第 9 条） | 未过期作业通常几十条；到点后日程仍在日历里（不会自动消失）——若将来觉得吵，再加"过期后删除"的策略 |
| **到点弹出未验证** | §5 第 10 项：探针日程写入成功但到点未弹通知；该模拟器上日历应用无法启动，无法排除"提醒依赖日历应用" | **需真机确认**；若真机同样不弹，则要考虑"系统日历这一载体也走不通"，届时只能申请代理提醒权益（§0 的选项 A） |
