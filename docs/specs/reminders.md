# 功能规格：作业截止前本地通知提醒

> 状态：开发中　·　关联 PRD：FR-18（与 FR-16 / FR-19 的边界见 §2）　·　分支：main
> 交互参照上游 `robertying/learnX` 的 `helpers/event.ts`（`saveAssignmentsToReminderOrCalendar` /
> `saveAssignmentEvent`）、`data/reducers/settings.ts`（`alarms` 默认值）、
> `screens/CalendarEvent.tsx`（设置项与开关联动）。**只取语义，不移植代码**（ADR-0001）。
> 平台能力换成鸿蒙的通知代理（`@ohos.reminderAgentManager`），上游那套 iOS `expo-calendar` 的
> Reminders 通道在鸿蒙没有对应物。

## 1. 背景与目标

作业有截止时间，但用户不一定会主动打开应用去看——**错过截止**是这个应用最实际的损失。
FR-18 让应用在截止前用**系统本地通知**提醒用户：登记在系统里、由系统在到点时刻弹出，
不依赖应用进程存活。

P1 已交付的 FR-07 给了"还剩几天"的列表文案，那是用户主动打开才看得到的；本 FR 补的是
**用户没打开应用时**那一段。FR-19（日历同步）是同一套"把作业搬到系统能力里"的编排，
但落点不同（系统日历），本 FR 不碰日历。

## 2. 需求（要什么）

**范围内**：

1. 设置页新增「提醒」一组，三项（对齐上游语义，去掉与日历强绑定的那些）：
   - **作业截止提醒**（开关，默认关）。关闭时不登记任何提醒，并清掉此前登记的。
   - **提前多久提醒**（整数分钟，默认 **1440** = 24 小时，对齐上游
     `assignmentReminderAlarmOffset ?? 24 * 60`）。仅在开关打开时出现。
   - **已完成不提醒**（开关，默认关，对齐上游 `assignmentCalendarNoAlarmIfComplete`）。
     仅在开关打开时出现。
2. 提醒登记规则（对齐上游 `saveAssignmentsToReminderOrCalendar` 的筛选）：
   - 只登记**未过期**的作业（上游 `dayjs(deadline).isAfter(dayjs())`，严格晚于当前时刻）；
   - 时刻 = **截止时间 − 提前量**；若该时刻已经过去（即"现在离截止已不足一个提前量"），
     **不登记**——系统不接受过去时刻的提醒，硬登记会直接报错；
   - 标题 = `作业名 - 课程名`（上游拼接方式）；正文 = 截止时刻（`YYYY-MM-DD HH:mm`）
     与正文摘要（有则另起一行）；
   - **去重按作业**：同一条作业只对应一条提醒，刷新多少次都不重复登记
     （上游用 `syncedReminderAssignments` 映射表；本项目改用**系统侧可读的 `groupId`**，
     见 §3.3 第 2 条）。
3. 同步时机（上游是"用户手动点一次"；本项目改为**自动对齐**，理由见 §3.3 第 4 条）：
   - 作业列表**加载成功后**（含手动刷新、提交后重拉）；
   - 用户在设置页改动上述三个设置后。
4. 点通知**打开应用**（`wantAgent` 指向本应用入口）。
5. 系统通知被关闭时，设置页在「提醒」这一组下**如实提示**（提醒登记了也弹不出来）——
   与 `testing-and-quality.md` §2 第 7 条"系统能力不可用不得影响主流程、只在设置页提示"同一口径。

**不做（范围外）**：

- **作业同步到系统日历**：属 FR-19（含 `assignmentCalendarAlarm` 那一整套、双提醒、
  日历事件时长、课程课表同步、地点省略）——本 FR 只做本地通知，不碰 Calendar Kit；
- **通知里的"已完成/补交"等标记与操作按钮**（上游 `'✅ ' + title` 前缀、snooze 按钮）：
  不做——通知是"提醒去看"，不是第二套 UI；
- **提醒的历史/已弹列表**：不做（系统通知中心就是历史）；
- **后台定时轮询新作业**：属 FR-25。本 FR 只在"应用内拿到作业数据"时对齐一次；
- 修改「提前多久提醒」时**不追溯重排**已弹出的历史通知，只重排尚未到点的登记。

### 3.3 关键规则

1. **纯逻辑与系统调用分离**（`testing-and-quality.md` §1.1）：筛选、时刻计算、标题正文拼接、
   文本解析、差量对齐全部在 `model/reminder.ets`，宿主侧可穷举；`native/reminderAdapter` 只做
   "把参数交给系统、把系统结果带回来"。
2. **去重键放 `groupId`，不落本地映射表**：`reminderAgentManager.getAllValidReminders()` 能读回
   每条提醒的 `reminderId` 与它自己的请求体，故把**作业键**写在 `groupId` 上，对齐时
   "读现状 → 比期望 → 撤多的、补少的"，无状态、可自愈（本地映射表一旦丢/错就永远对不上，
   而上游正是这么做的）。**作业键用 `课程 id:作业 id`**：上游只用作业 id，但
   `xszyid` 是否跨课程唯一无从保证，复合键不会串（与 FR-08 附件目录多加两层同一考虑）。
3. **"该撤哪些"按三件事判**：不在期望集合里的（作业已提交且勾了"已完成不提醒"、已截止、
   已不再是当前学期的数据）要撤；在期望集合里但**时刻变了**（截止时间被老师改了）要撤了重登；
   其余原样留着，避免每次刷新都重写系统提醒。
4. **自动对齐而不是手动同步**：上游要用户进设置页点一次同步，忘记点就等于没提醒——而
   "不被落下"正是这个功能的价值。故改为**作业数据一落地就对齐**（加载成功 / 设置变更），
   行为对用户可见（设置页写明"作业数据刷新时会自动对齐"）。
5. **关闭开关即清**：关闭时不登记任何提醒，并撤掉此前登记的全部——不留"关了还在弹"的幽灵提醒。
6. **条数上限**：系统对单应用提醒数量有限制（超限报 `1700002`），故按**触发时刻从近到远**
   取前 N 条（N 见 §6）。到点后提醒从"有效提醒"里消失，下次对齐自动补上更远的——不会因为
   一次截断就永久漏掉后面的作业。
7. **过去时刻不登记**：`triggerTime <= now` 直接跳过（这条不是为了好看——系统对过去时刻
   要么报错、要么立刻弹一条无意义通知）。
8. **截止时间解析不出（`deadlineTime === 0`）不登记**：与 FR-07 列表同一口径——不知道截止时间
   就不拿它做提醒。
9. **差量对齐是幂等的**：同一份作业数据连跑两次，第二次一定是"无登记、无撤销"（下面的验收项
   用纯逻辑钉住这一点）。
10. **通知正文不含中英文案**：提醒标题/正文在**系统通知**里显示，由 `native` 侧拼装成纯字符串，
    取不到 `Resource`（架构不变量 §1：`model`/`native` 不持有 `Resource`）。故正文只用
    **语言无关**的数据：截止时刻（数字）与作业正文摘要（服务端数据）。界面文案（设置页各项）
    照常走中英文案资源。
11. **失败不影响主流程**：登记失败（系统未启用通知、超限、服务不可用）只记日志；
    作业列表与设置页的其它操作不受影响（`ARCHITECTURE.md` §5.5 "尽力而为"）。

## 5. 验收标准

**自动化可验证（单元测试，不依赖设备）**：

1. 筛选与时刻：只收"未过期"的作业；`triggerTime = deadlineTime - offset*60000`；
   `triggerTime <= now` 的不登记；`deadlineTime === 0` 的不登记；
   勾了"已完成不提醒"时已提交（`submitted`）的不登记，未勾时照样登记。
2. 条目内容：标题为 `作业名 - 课程名`；正文含 `YYYY-MM-DD HH:mm` 形式的截止时刻，
   摘要非空时另起一行；**不含任何中文/英文界面文案**（只有数据）。
3. 条数上限：超过上限时按**触发时刻从近到远**截断，且截断后仍是稳定顺序。
4. 时间戳 → 提醒时刻：年月日时分取值正确（含**跨月/跨年边界**与**月份从 1 起算**这条约定）；
   换算与本地时区一致（用 `Date` 的本地字段）。
5. 差量对齐：`(期望, 现状) → (要登记的, 要撤销的)` 四类情形都不漏——
   新增登记、已截止撤销、时刻变更则撤销并重登、完全相同则**两者皆空**（幂等）；
   现状里没有 `groupId` 的（非本功能登记的）**不动**。
6. 偏移文本解析：`0` 与正整数（含前后空格）通过；空串 / 非数字 / 负数 / 带小数 /
   超过上限（14 天）→ 拒绝（上限只为挡住多打几个 0 的手误，不是业务约束）。
7. 静态门：`check arkts`（主 + 测试显式传路径）、`check lint` 零错误；`build` 成功；
   `check-l10n` 键集合一致。

**设备验收（模拟器/真机，已登录）**：

8. 设置页出现「提醒」组：开关默认关，打开后出现"提前多久提醒"（默认 1440）与"已完成不提醒"；
   关掉后两项消失；改动被持久化（重启后仍在）。
9. 打开开关、进作业标签让数据加载后，**系统里确实登记了提醒**：用
   `getAllValidReminders()` 读回（或系统通知设置里的应用提醒列表）核对条数与作业一致，
   且**重复刷新不产生重复登记**。
10. 关掉开关后，此前登记的提醒**全部消失**（同一读回手段核对）。
11. **到点会弹**：登记一条短时间内会触发（把提前量设到"距截止不足该提前量"之外的构造见 §6）
    的提醒，确认系统在该时刻真的弹出通知，且**点击打开本应用**；这条同时**验证 §6 里
    "月份从 1 起算"的约定**（起算错一个月则该时刻根本不会到）。
12. 提醒登记失败（系统通知被关闭）时：作业列表与设置页一切照常，设置页「提醒」组下**给出提示**。

**需用户确认**：第 11 项要在**真机**上确认一次（模拟器能否弹系统通知见 §6）；实际到点的提醒
时刻与用户预期一致。

## 6. 风险 / 待定

| 项 | 说明 | 处置 |
|---|---|---|
| `LocalDateTime.month` 从 0 还是从 1 起算 | SDK 的 d.ts 只写"Value of month"，官方样例用 `month: 1` 配"1 月"的语境但不足以当结论 | 按**从 1 起算**实现，并用 §5 第 11 项的"真弹一次"实验钉死；若实验推翻则改 `toReminderDateTime`（纯函数，一处改） |
| 模拟器能否弹系统通知 | `reminderAgentManager` 依赖系统通知服务，模拟器上可能不可用（此前踩过"模拟器没有 svc"） | 先在模拟器上跑 §5 第 9/10 项（登记与撤销，只需服务端可用）；第 11 项若模拟器上不弹，如实记为"需真机验证" |
| 条数上限 N | `1700002` 的具体阈值未查证（也无从在此查） | 取 **30** 条（按触发时刻从近到远），并在日志里记下被截断的条数；若设备实测阈值更低，改这一个常量 |
| 提醒在**应用未运行时**是否仍会弹 | 系统代理提醒的设计就是脱离应用的，但本项目尚未实测 | §5 第 11 项顺带验：登记后**杀掉应用**再等到点，看是否照弹 |
| 切换学期会撤掉旧学期的提醒 | 对齐只按"当前学期的作业数据"算，切到 B 学期后 A 学期未截止的作业会失去提醒 | 有意如此（应用此刻展示的就是 B 学期）；在设置页说明"对齐的是当前学期的作业"。若用户希望保留，改法是把已登记项并入期望集合——待用户表态 |
| 提醒时刻**晚于**截止 | 偏移为 0 时时刻=截止时刻 | 允许（上游同样允许）。偏移 0 的登记只在"截止仍在未来"时发生，不会登记过去时刻（§3.3 第 7 条） |
