# 功能规格：进入应用时后台同步最新数据（预载通知与文件）

> 状态：开发中　·　关联 PRD：FR-25　·　分支：main

## 1. 背景与目标

现在的取数是**按需**的：学期在登录后就准备好、课程跟着学期准备好（这两条是为了把"内部依赖"
从用户操作里拿掉，见 `Main` 的两段注释），但**通知与文件要等用户真的切到那个标签才开始拉**。
实测启动日志能看清这个缺口——应用 13:18:25 起，`fileStore` 的请求直到 **13:18:51**（用户切到
文件标签时）才出现，中间 26 秒这个标签是空的。

本 FR 把这两个维度的取数**提前到进入应用时**：切到通知/文件标签时数据已经在那儿，
列表直接出现，而不是先转圈。

## 2. 需求（要什么）

**范围内**：

1. **登录后（含冷启动恢复登录态）课程一就绪，即预载"通知 + 文件"**，不等用户切标签；
2. **后台**：不阻塞 UI、不弹任何提示；**失败不打扰**——页面照旧有自己的错误态与「重试」，
   预载失败与否不改变用户看到的交互；
3. **串行执行**：通知 → 文件。两个维度各自都是"按课程扇出"，同时在飞会把峰值并发翻倍
   （各自 `FANOUT_LIMIT=4`），对同一个小服务器不友好；用户并不在等，慢一点没代价；
4. **幂等**：同一个学期在一次运行里只发起一次预载；用户手动刷新、切学期仍走各自原有路径
   （store 内部按"学期 + 课程集"签名比对，本来就不会白拉）；
5. **只为当前学期**取数，范围与标签页一致（当前学期全部课程，不因展示层的筛选而收窄）。

**不做（范围外）**：

- **作业不预载**：它是四个维度里**最贵**的一个（每门课 3 个端点 + 逐条详情），
  而"作业"是挑着看、不是进来就要的场景。用户切到作业标签时再拉（现状不变）；
- **不预载文件内容**：预载的是**元数据列表**，不是文件字节。"把文件下下来"是 FR-10 的动作，
  必须由用户逐份触发——后台批量下载会烧流量、占空间，且用户没要；
- **不做后台常驻/定时同步**：应用不常驻后台，进程被杀后自建定时器不会响（同 `API.md` §3
  里"提醒改用系统日历"那条道理）；本 FR 只覆盖"用户打开应用"这一时刻；
- **不做网络类型感知**（移动网络下少拉）：没有用户诉求，且要新增系统能力/权限；
- **不新增"同步中"的全局指示器**：预载是后台行为，不该在界面上占位置；要看它有没有发生，
  看日志（§5 的验收就是这么做的）。

## 3. 设计（怎么做）

### 3.1 上游事实（对照基线）

| 事实 | 出处 |
|---|---|
| 上游**没有**启动预载：每个列表屏自己 `useEffect` + `useSelector(courseIds)`，进屏才 dispatch | `src/screens/Notices.tsx`、`src/screens/Files.tsx` |
| 上游的刷新是"下拉刷新"与进屏各一次（`handleRefresh` 同时供两者用） | 同上 |

> 与上游的**有意不同**：本项目把"通知 + 文件"提到进入应用时预载（PRD FR-25 的要求），
> 上游那种"进屏才拉"在本项目的观感是"切标签先转圈"。

### 3.2 模块与文件

| 层 | 文件 | 职责 |
|---|---|---|
| `common` | `prefetch.ets`（新） | **纯逻辑**：预载目标与顺序、以及"什么时候不该预载"的判据（可穷举测试） |
| `viewmodel` | `startupSync.ets`（新） | 编排：按顺序调用两个 store 的 `ensureLoadedFor`，记日志、吞掉异常、按学期去重 |
| `pages` | `Main.ets`（改） | 订阅课程状态；课程就绪时调 `StartupSync.run(semesterId, courses)` |

> `Main` 里已是同类模式（订阅学期 → 拉课程），新增的订阅与既有的一起在 `aboutToDisappear`
> 里反订阅，保持"订阅与反订阅成对"（审查遗留的订阅计数口径）。

### 3.3 关键规则

1. **判据与顺序放在纯函数里**：`prefetchTargetsFor(semesterId, courseCount)` —— 学期为空或
   课程数为 0 时返回**空数组**（没有目标就一条请求都不发），否则返回 `['notices', 'files']`。
   作业**不在返回值里**（§2 的范围外，用测试钉住，防"顺手补上"）。
2. **一次运行里一个学期只预载一次**：`StartupSync` 记住上次发起预载的学期。理由是课程状态的
   每次 `notify()` 都会触发订阅者，而去重若只靠下游 store 的签名比对，
   **失败时签名不会被记下**，几次 notify 就会重拉几次（风暴）。
   显式重试仍归用户：切开那个标签 → 页面报错误态 → 点「重试」。
3. **串行、按顺序 await**：见 §2 第 3 条。
4. **异常在此终结**：两个 store 的 `ensureLoadedFor` 内部已把失败归类进错误态（不抛），
   但 `StartupSync` 仍把整段包在 try/catch 里并只记日志——预载失败**不得**冒到 UI。
5. **日志是验收依据**：开始时记一行（学期 + 课程数 + 目标顺序），每个目标完成记一行；
   加上两个 store 自己已有的"加载完成 数量=…"，启动日志里能直接看出预载发生了。

## 5. 验收标准

**自动化（已过）**：

1. `prefetch` 4 组用例：学期为空 / 课程数为 0 或负数 → 空数组；正常 → `['notices','files']`
   且**不含作业**、顺序稳定；
2. 静态门：`check arkts` 主 94 / 测试 26 文件 0 error、`check lint` 0 error、`build` 成功、
   **282 例单测 0 失败**。

**设备验收（模拟器 learnx / 真实账号，2026-09-29）**：

3. ✅ **冷启动后全程没有点过任何标签**，启动日志里就出现了完整序列（毫秒见先后）：

   ```
   14:02:38.739 [courseStore] 课程加载完成 学期=2026-2027-1 数量=12
   14:02:38.740 [startupSync] 启动预载开始 学期=2026-2027-1 课程数=12 目标=[notices files]
   14:02:39.363 [noticeRepository] 通知加载完成 课程数=12 失败=0 通知数=12
   14:02:39.363 [startupSync] 启动预载完成 目标=notices
   14:02:39.882 [fileRepository] 文件加载完成 课程数=12 失败=0 文件数=36
   14:02:39.882 [startupSync] 启动预载完成 目标=files
   ```

   串行顺序与 §3.3 第 3 条一致；**文件在整个会话里没有任何别的东西能触发**——
   这就是"预载真的发生了"的证据（对比 §1 引的旧日志：那时文件要等用户切标签、晚 26 秒）。
   该会话里**没有**任何 `assignmentRepository` 的预载日志（作业仍按需拉：
   切标签时才出现 `作业请求在途` → `作业加载完成`）；
4. ✅ 切到「文件」标签后日志**不再出现** `fileStore 请求在途` 或 `文件加载完成`——
   标签页的 `ensureLoadedFor` 比对签名后直接跳过，列表直接就是数据（§3.3 第 4 条的幂等）。

## 6. 风险 / 待定

| 项 | 说明 | 处置 |
|---|---|---|
| 冷启动开销 | 进应用即多两轮扇出（各 ≤12 个请求），可能拖慢首屏感知 | 预载不阻塞 UI（不 await 在关键路径上），且串行把峰值并发压在 4；若实测卡顿，改为"首屏静置 N 秒后再预载" |
| 每次启动都重拉 | 应用每次冷启动都会重新拉通知/文件列表（不做本地缓存判定） | 与现状一致（标签页本来就是进屏必拉）；若将来要"多久内不重复拉"，那是缓存策略，需单独立项 |
| 预载失败后的沉默 | 失败只进日志，用户在那个标签里才会看到错误态 | 有意为之（§2 第 2 条）：后台动作不该弹提示。页面侧的「重试」是唯一出口 |
