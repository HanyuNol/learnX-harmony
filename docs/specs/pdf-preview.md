# 功能规格：应用内预览的交互打磨（PDF / 图片 / 文本 / 音视频）

> 状态：开发中　·　关联 PRD：**FR-21**（原表述为"PDF 文件原地查看"，本次**重划范围**，见 §1）　·　分支：main
> 交互参照上游 `robertying/learnX` 的 `screens/FileDetail.tsx`（详情页进页即渲染）。
> **只取语义，不移植代码**（ADR-0001）。

## 1. 为什么要重划范围（2026-09-29）

用户指出"PDF 不是已经能看了吗"——核对属实：**"能看"这一条已由 FR-08 交付并在真机验证过**，
PRD 里 FR-21 那行字（"PDF 文件原地查看"）**按字面已经没有增量**。现状（代码事实）：

- 「预览」按钮只在"浏览器渲染得出来的类型"上出现（`FileDetail.ets:214`、`canPreviewInApp` 白名单：
  pdf/html/图片/纯文本/音视频），点它**先确保文件在沙箱（未下过则先下载）**再交给 ArkWeb；
- 预览区是 `Web` + `.fileAccess(true)` + `file://` 绝对路径（`FileDetail.ets:250-256`，
  两个硬条件见 `files.md` §3.3 第 9 条），作业附件走同一套（`AssignmentDetail.ets:199,330`）；
- 真机确认过 Chromium 的 PDF 文档视图确实在工作（`pdf_document_helper`）。

**缺口不在"能不能看"，而在"看得顺不顺"**，实测/读码得到的四条：

| 缺口 | 现状 | 后果 |
|---|---|---|
| 预览区固定高 720vp | `.height(720)` 写死 | 长文档只能在一个半屏窗口里滚，翻页很累 |
| 没有"关闭预览"入口 | 点过预览后 `previewUri` 一直非空，只能往下滚或返回上一页 | 想接着看文件信息得先退出去 |
| 渲染期间没有反馈 | 只有下载阶段有"下载中…"；交给 ArkWeb 后到渲染出来这段时间界面无变化 | 大文件看着像"点了没反应" |
| 渲染失败静默 | `onErrorReceive` 只写日志 | 打不开时用户看不到任何原因（`files.md` §3.3 第 9 条那类失败会重现） |

故本 FR 的**新范围＝预览的交互与状态打磨**，交付物见 §2。

## 2. 需求（要什么）

1. **预览占用可用空间**：进入预览后元信息与动作区收起，预览区铺满页面剩余高度（不再写死 720vp），
   退出预览即恢复原布局。
2. **明确的进入 / 退出**：点「预览」进入；预览态右上角有**关闭**入口（与系统返回键都能退出），
   退回后元信息与动作区原位恢复。
3. **加载态**：进入预览后立刻显示"正在打开…"（含大文件要先下载的情形），渲染完成即撤下。
4. **失败态**：渲染失败时给出**可读提示**并提供两个出路——**重试**（重新交给 ArkWeb）与
   **交给其他应用打开**（与既有「打开」动作同一路径），不再静默。
5. **手势与缩放**：显式开启手势缩放（`zoomAccess(true)`）与平滑缩放，允许用户在预览里双指放大
   看小字；纵向滚动沿用 ArkWeb 自带行为。
6. **两个入口一致**：文件详情与作业附件详情的预览都具备以上行为（同一套组件，不再各写一遍）。

**不做（范围外，且理由明确）**：

- **页码跳转 / 全文搜索 / 缩略图侧栏**：这些需要自己渲染 PDF，而架构不变量 §2 **禁止引入第三方
  PDF 库**（含 PDF.js 一类 JS 库）；ArkWeb 内嵌的是 Chromium 的 PDF 查看器插件，
  我们**无法**对其 UI 或内部状态编程。如实记为"平台能力边界"，不是偷懒；
- **记住上次阅读位置**：同样落到"读不到内嵌查看器的滚动位置"，**未验证能否做到**（见 §6），
  不先做；
- **强制深色**：`Web.darkMode` 会把 PDF 反色，插图与彩色标注会失真，故不做；
- **另存为 / 分享 / 打开方式**：已有，属 FR-08 / FR-23，不重复；
- **缓存与离线**：属 FR-08 的下载管理，不重复。

## 3. 设计（怎么做）

### 3.1 上游事实（对照基线）

| 事实 | 出处 |
|---|---|
| 详情页**进页即自动下载**，并把文件**渲染在应用内**：`pdf` 用 PDF 组件、其余可渲染类型用 `WebView` | `screens/FileDetail.tsx:263-300`、`helpers/fs.ts:202-210` |
| 「外部打开」只是附加动作（Android 上 `IntentLauncher`） | 同上 |
| 上游没有加载/失败态处理（`react-native-pdf` 自带） | 同上 |

> 与上游的差别：上游在 iOS/Android 上用的是**原生 PDF 组件**（能控制页码/缩放），
> 本项目受"禁第三方 PDF 库"约束，只能用系统 ArkWeb 的 Chromium 查看器——**能力边界不同，
> 不能照抄它的交互清单**。

### 3.2 模块与文件

| 模块 | 文件 | 职责 |
|---|---|---|
| `components` | `PreviewPane.ets`（新） | **一个可复用的预览面板**：沉浸布局、关闭入口、加载态、失败态（重试 / 交其他应用）、Web 的交互属性集中一处 |
| `pages` | `FileDetail.ets`（改） | 用 `PreviewPane` 替换原来那段 `Web`；修掉头部那句已过时的"不做预览（属 FR-21）"注释 |
| `pages` | `AssignmentDetail.ets`（改） | 同上，附件预览共用同一面板 |
| `common` | `texts.ets` + 中英文案（改） | 新增：正在打开预览 / 预览打不开 / 关闭预览 / 重试 |

### 3.3 关键规则

1. **预览的两个硬条件不能动**（`files.md` §5 明示）：`.fileAccess(true)` 与
   **`file://` + 绝对路径**。改动预览相关代码时先看 `native/fileAdapter.previewUrlOf` 的注释——
   喂错形态会被 ArkWeb **静默拒绝**，现象与"文件不存在"分不开。
2. **失败要给出路，不只是提示**：预览打不开时给"重试"与"交给其他应用"两个动作——
   `files.md` §5 已记录过"设备上没有能打开该类型的应用"这类失败，用户需要的是下一步能做什么。
3. **加载态覆盖两个阶段**：下载（已有"下载中…"文字）与渲染（本次新增"正在打开…"）。
   两阶段都不受应用控制（网络与渲染都在系统侧），所以只能"如实显示正在发生什么"，不能给假进度。
4. **退出预览即恢复**：预览态只改本页布局（元信息/动作区 `if` 掉），不改变任何存储或状态，
   退出后与进入前完全一致。
5. **一套组件两个入口**：文件详情与作业附件详情的预览行为必须一致，避免"一处打磨、一处忘"。
