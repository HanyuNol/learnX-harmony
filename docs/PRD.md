# 产品需求文档（PRD）：learnX 鸿蒙版

> 需求的单一真源（WHAT / WHY），也是产品的**需求登记册 + 路线图**——全生命周期都在记，不是一次性文档。每个需求在 §4 加一行 FR（带优先级/期 + 状态），交付即标版本；§4 FR 表是迭代中最常动的部分（🔥 高频），分期（§7）只是其中很小、很静的一页粗线条规划。单功能的详细规格放 `docs/specs/`，PRD 只保留"一行 FR + 期 + 状态"的索引级。

## 1. 背景与目标

清华大学网络学堂（learn.tsinghua.edu.cn）是校内师生获取通知公告、作业、课件文件与课程信息的核心入口。开源项目 [robertying/learnX](https://github.com/robertying/learnX) 以 React Native 实现了体验良好的移动端客户端，但它无法运行在 HarmonyOS NEXT 上——HarmonyOS NEXT 以 OpenHarmony 为底座，不含 AOSP/Android 运行时，也不承载 React Native 的 Android/iOS 原生层。

本项目把 learnX 的功能在 **HarmonyOS NEXT 上以 ArkTS / ArkUI 原生方式重建**，目标产物是一个可在 HarmonyOS 手机上真实使用的网络学堂客户端。

一句话价值主张：**让清华师生在鸿蒙设备上，用原生的体验访问网络学堂的全部常用信息。**

### 非目标

- **不做跨平台复用**：不移植 React Native 代码或其 JS 生态依赖，不引入 RNOH（理由见 ADR-0001）。这是重建，不是套壳。
- **不做 Android / iOS 端**：不维护多端共享代码。上游 learnX 继续负责 Android / iOS / macOS。
- **不做 Web 版**、不做元服务卡片、不做服务端：本项目只产出 HarmonyOS 客户端应用。
- **不代理或转发校园服务**：应用直连校方既有接口，不自建中转服务、不缓存用户数据到第三方。
- **不承诺脱离校园网可用**：网络学堂本身要求校园网或校方 VPN，本项目不改变该前提（见 §5 NFR-NET）。

## 2. 角色

- **清华在校学生（主要用户）**：查通知、交作业、下课件、看课程安排。多数在校园网或校方 VPN 下使用。
- **清华任课教师**：关注通知发布与作业批改状态（上游未做教师专属功能，本项目同样不做）。
- **开发者 / 维护者**：在 SDD 治理下迭代本项目的人（含 AI Agent）。
- **上游 learnX 与 thu-learn-lib**：契约参照方。上游接口语义变更是本项目的外部风险源。

## 3. 用户故事

- 作为学生，我希望用学号和密码（或统一身份认证）登录网络学堂，以便在手机上查看我的课程信息。
- 作为学生，我希望不被反复要求登录，以便打开应用就能直接看到内容。
- 作为学生，我希望按学期切换并浏览通知、作业、文件、课程四个维度，以便快速找到要看的东西。
- 作为学生，我希望把课件文件下载到本地并直接打开，以便离线阅读。
- 作为学生，我希望作业截止前收到提醒，以便不遗漏提交。
- 作为学生，我希望把作业截止时间同步到系统日历，以便和我的日程放在一起看。
- 作为学生，我希望在弱网或断网时看到明确的错误提示而不是白屏，以便知道是网络问题还是应用问题。
- 作为开发者，我希望规格先行、每步有验收，以便跨会话、跨 Agent 迭代时不漂移。

## 5. 非功能需求（NFR）

- **NFR-NET｜网络前提**：网络学堂（`learn.tsinghua.edu.cn`）与统一身份认证（`id.tsinghua.edu.cn`）仅在校园网或校方 VPN 内可达。应用必须在该前提下工作，并对不可达给出明确提示，不得把网络不可达误报为应用缺陷。
- **NFR-PERF｜性能**：冷启动到首屏可交互 ≤ 3s（校园网、已登录）；通知/作业/文件列表滚动不掉帧；单次列表请求超时上限 15s，超时呈现错误态而非无限等待。
- **NFR-SEC｜安全**：凭据与 Cookie 一律经系统加密能力存储；禁止明文落盘、禁止写入日志、禁止硬编码。详见 `SECURITY.md`。
- **NFR-COMPAT｜兼容**：按项目锁定的 HarmonyOS SDK 版本编译（见 `ARCHITECTURE.md` §6），并在手机与平板两种设备形态上验证布局。
- **NFR-MAINT｜可维护**：分层单向依赖；ArkTS 编码遵守语言限制（禁 `any`、禁反射、禁动态属性）；每个 FR 有可追溯的验收。
- **NFR-I18N｜国际化**：新增用户可见文案必须同时提供中英文，不得只写中文。
- **NFR-A11Y｜可访问性**：交互控件具备无障碍标签，支持系统字号缩放。

## 6. 验收标准

项目整体"做完"以下列判据为准，**测试通过不替代实机验收**：

1. 所有 P1 FR 在真机或模拟器上可演示，行为与 `docs/specs/` 中各自验收标准一致。
2. **【需用户确认】** 在校园网（或校方 VPN）环境下，用真实清华账号完成一次完整链路：登录 → 切换学期 → 浏览通知/作业/文件/课程 → 下载并打开一个课件文件。→ 该项必须由用户在真实账号与真实网络下确认通过，自动化测试不能替代。
3. **【需用户确认】** 在鸿蒙手机上安装运行，冷启动、列表滚动、页面跳转无明显卡顿或崩溃。→ 需用户实机确认。
4. 断网/网络不可达时，应用呈现明确错误态且不崩溃（可在无校园网环境验证）。
5. 凭据与 Cookie 不出现于任何日志、源码或明文存储文件中（可静态检查 + 运行时抽查验证）。
6. `devecocli check arkts` 与 `devecocli check lint` 对本项目零错误。
7. 中英文文案齐备；深色模式下无不可读文本。
8. 未登录状态、登录态失效、接口返回异常三种情况均有明确引导，不出现白屏。

> 上述第 2、3 项为**实机验收项**：在 P1 全部达成后由用户执行确认。在此之前，P1 的 FR 一律不得标 `已交付`。

## 7. 分期（路线）

各期只描述**主题 / 目标**；**具体哪个 FR 属于哪期，以 §4 FR 表的优先级 / 期列为唯一来源**——加需求即在表里标期，本节不重复列编号、不随 FR 增长而改。

- **第一期（MVP）**：把"能登录、能看内容"立起来——登录与凭据、学期切换、通知/作业/文件/课程四个维度的浏览与下载、导航、主题与国际化、错误反馈、设置页。
- **第二期**：把"好用"补齐——搜索、提醒与日历同步、作业提交、PDF 与富文本渲染、分享互通、生物识别、后台同步、大屏自适应。
- **第三期**：把"完整与打磨"收尾——课程信息共享、更新检查、动效与无障碍。

> **分期不会堆到上百**：期是粗粒度路线图横轴，数量很少（走到成熟通常 3~6 个），一期含很多 FR、跨很多版本。**产品成熟（1.0 后稳态迭代）就不再加"第 N 期"**，改按版本（CHANGELOG / tag）+ 功能（FR 表 / specs）组织。
> 某期是否完成，看 §4 表里该期 FR 的"状态"是否都 `已交付`——进度不在本节维护。
