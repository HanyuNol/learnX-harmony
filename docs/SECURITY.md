# 安全说明：learnX 鸿蒙版

> 信任模型、敏感数据处理、外部输入校验与漏洞报告渠道。安全模型变化时更新。

## 1. 信任模型

**可信**：用户自己的设备与应用沙箱；系统提供的加密存储与能力 Kit；校方服务（`learn.tsinghua.edu.cn`、`id.tsinghua.edu.cn`）。

**不可信**：用户网络路径上的中间人；应用收到的全部外部输入（用户输入、WebView 加载内容、分享进入的文件、外部服务响应）。

**信任边界**：

```
[用户设备]  应用沙箱 ──(加密存储: 凭据/Cookie)── 唯一凭据载体
     │
     └─ HTTPS ─→ [校方服务]        ← 唯一直连的服务端，不中转、不代理
     └─ HTTPS ─→ [api.tsinghua.app] ← 第三方非官方服务（P3，可放弃）
```

- **本项目不含服务端**，因此不存在"服务端被攻破"面；也不存在本项目的服务端保管用户凭据的场景（见 ADR-0006）。
- **攻击面**：① 应用内的 WebView（统一身份认证页面）；② 外部服务响应与 HTML 解析；③ 从其他应用分享进入的文件；④ 本地存储的凭据。

## 2. 密钥与敏感数据

- **凭据（学号、密码、指纹派生值）与 Cookie 只能存在于系统加密存储中**，经 `storage.CredentialStore` 统一读写；其余模块不得直接访问凭据存储。
  > **唯一例外**：WebView 主导登录时，学号与密码必须注入页面表单（否则"预填"无从谈起，用户得手输）。
  > 该例外以**内存驻留、用完即清**为界：`SsoInjection` 不进 ArkUI 的 `@State`（组件状态会进无障碍树）、
  > 不入日志、不落盘；离开网页登录流程即置空（`AuthStore.clearInjection`）。
- **会话 Cookie 由 `network.WebCookieStore` 承载**（`webview.WebCookieManager`，进程级、可落盘）：
  WebView 与 API 请求共用同一份会话——这既是"重放页面表单体"能成立的前提（见 ADR-0008）。
  它不进应用自建的明文文件；`CredentialStore` 仍只负责学号、密码与设备指纹。
- **严禁**：
  - 硬编码任何凭据、令牌、密钥；
  - 凭据或 Cookie 明文落盘（含缓存、日志、崩溃转储、临时文件）；
  - 把凭据或 Cookie 写入日志（`common/` 的日志工具须对敏感字段脱敏）；
  - 把凭据经应用间互通（分享、通知、日历）传递。
- **凭据不得入库**：`git` 历史中不得出现任何真实账号信息，包括测试用例与调试脚本。
- **生物识别**（FR-24）：仅作为本地解锁手段，**不得替代或复制凭据存储**；认证失败必须回退到密码输入。
- **轮换**：用户改密或登出时，加密存储中的**学号与密码**必须清除。
  **设备指纹例外保留**：它是设备标识而非凭据（不含用户信息、不由用户输入、服务端本就存有副本），
  且服务端靠它把本机认成"同一台已登记的信任浏览器"——清掉它会导致每次登出再登录都被当成新设备，
  每次都要重新多因子认证（2026-09-27 真机实测，见 `docs/specs/auth-login.md` §3.5 与 §11.7）。

## 3. 外部输入

- **所有外部输入一律校验后再用**：
  - 网络响应按"不可信"处理：解析失败归入"解析失败"错误类，不得把异常直接抛给 UI（见 ARCHITECTURE §5.4）。
  - **统一身份认证页面的注入是有边界的例外**（ADR-0008）：登录由 WebView 主导，因为多因子认证的
    验证码只能由用户在真实页面上输入，"纯 API 登录"没有任何位置承载这一步。注入脚本
    `resources/rawfile/sso_inject.js` **只允许做五件事**：① 预填学号与密码（置只读，用户要改须关页面重来）；
    ② 页面询问"是否信任此浏览器"时替用户答"是"并写入应用持久化的设备指纹；③ 把提交时的完整表单体
    回传应用（其中的 `fingerPrint` / `fingerGenPrint` / `fingerGenPrint3` 只能这样获得）；
    ④ 回报页面结构异常；⑤ 就地把 `navigator.storage.estimate` 与
    `navigator.webkitTemporaryStorage.queryUsageAndQuota` 的**存储配额读数**抬到阈值之上——
    校方页面判断"隐私或匿名模式"用的第三方库在移动端 WebView 上会按存储配额误报，
    而该判据是客户端启发式、**不是安全控制**（边界与"必要性待实验"见
    [ADR-0010](adr/0010-injection-raises-storage-quota-reading.md)）。
    约束：脚本**只匹配 `id.tsinghua.edu.cn` 来源**；**不代填、不代答验证码**（那是用户的步骤）；
    第 ⑤ 件事只**就地替换那两个方法**、不替换对象本身，且**抬不动时静默退让**；
    选择器与接口路径集中在该一个文件维护，便于随校方改版修改。
    > 注入脚本会把学号与密码写入页面 DOM——这是该流程不可回避的部分。它只存在于页面内存与本次会话中：
    > 不入日志、不落盘、不回传。运行时抽查见 spec §5 第 11 项（实测 hilog 全量 4427 行中 0 命中）。
  - **除上述 SSO 登录页外，任何 WebView 都不得注入脚本或改变页面行为**（如后续的富文本正文渲染），
    也不得解析、记录页面内容中的敏感信息。
  - HTML 正文渲染：按实际需要的标签做白名单式清洗，**不得整体信任服务端返回的 HTML**，不得执行其中的脚本。
  - 从分享/文件选择进入的内容：仅处理白名单内的 MIME 类型；未知类型直接忽略；不按外部传入的路径直接读写文件。
- **路径**：涉及本地文件路径的操作须校验目标位于应用可写目录内，防目录穿越。

## 4. 漏洞报告

本项目为学习/自用性质的开源客户端，无商业支持渠道。

- 发现问题请通过仓库 Issue 报告；**涉及凭据泄漏、越权、目录穿越等安全问题请勿在公开 Issue 中附真实账号、Cookie 或可复现的敏感数据**。
- 响应预期：维护者按可用时间处理，不承诺响应时限。
- 披露策略：修复发布后再公开细节。

> 若本项目未来对外分发，本节须补充明确的联系渠道与响应时限。
